## 受入を止める差分

1. **[P1] Source 現行 access / owner / retention の hard semantics は未検証。** `Access` は bare `ResourceId` と合成 `deny:<id>` context だけを評価し（`src/main.rs:81-93`）、Source 2 の同じ裸 ID に別の認可判断を与えない。`bench.py:38-87` は同じ合成 denied 値で 1-hop の可視性を計算する。storage の cross-Source 分離は確認できるが、Source 別 `CurrentAccessEvaluatorPort`、現在権限取消、owner spoof / FolderPlacement mapping、Version 直接評価、`SESSION_ONLY` / `NO_RETENTION` 拒否は確認できない。凍結契約 §2/§6/§9 と計画 `P3-P00/P04` の current-access / retention gate を満たさない。
2. **[P1] persisted incidence と canonical relation の整合は未検証。** PG / Neo4j の lookup は `borrower` incidence/edge で relation を選ぶが、その後は保存済み `relation.payload` の participant 集合を独自 Python evaluator に渡す（`bench.py:188-197,274-299`）。他 role の participant 行/edge を再構成して payload と照合しない。redb の 7 query parity は、保存済みの全 relation/resource 行を load して **memory oracle を再構築**する（`src/main.rs:405-433,521-542`）。redb incidence query の検査は特定 seed の件数と wrong-generation のみ（`:543-547,591-605`）。したがって三方式の traversal/access の完全 parity、破損した incidence の検出、同じ canonical Graph digest はこの結果から導けない。positive/negative 7 ケースは有用だが、production `GraphTraversalPlan` の budget、multi-hop、path/candidate identity の代替ではない。
3. **[P1] P3-P04 の predeclared hard gate / provenance が未完。** 計画 `p3-graph-plan.md:52-95` は seed `0x50330001`、64/96・1,024/1,536・8,192/12,288 と high-degree、Neo4j `neo4rs`/Bolt、少なくとも 200 sample/class、cold/warm 1/2/4/8 reader + writer、raw sample JSON、三方式の restart/restore/fault、PG の publish/pin/GC/guard 等の disposable probe を指定する。実 artifact は固定数式 ID と記録用 seed `314159`、100/1,000/3,000 group、Neo4j HTTP、100 warm raw lookup、上記 fault の大半が未実施（`src/main.rs:96-101,337-345`、`bench.py:308-347`、`report.md:65-66`）。計画が worker dispatch 後に固定された事情は差分の説明になるが、受入済みの変更にはならない。`qualification-report.json` と独立 `p3-graph-selection.md` も存在しない。欠測を PASS とする選定関数/テストもない。
4. **[P2] 保存列の temporal / canonical digest 資格は限定的。** PG は五 timestamp の NUMERIC+offset 列を作り正 offset の 1 probe を記録したが、`resource()` と path evaluator は JSON `payload` を読む（`bench.py:111-135,195-197,38-44`）。列からの roundtrip、負 offset、`NULL` と空 freshness basis の区別、全 interval 境界、`graph_content_digest` の full↔incremental parity は未検証。relation-only full 比較も 7 seed の relation payload 集合であり、全 relation の canonical digest / path/evidence 一致ではない（`bench.py:326-335`）。redb は全 relation 集合比較があるが digest はない。
5. **[P2] 性能・容量値は探索値。** PG は psycopg、Neo4j は Query API HTTP、redb は同 process read transaction。Python の percentile は index floor（`bench.py:90-92`）、Rust の redb は別 index式かつ整数 µs（`src/main.rs:517-520,558-570`）。PG/Neo4j の size は cross-Source stage 前、redb file size は後（`bench.py:336-347`、`src/main.rs:591-606`）。Neo4j は複数 HTTP transaction、PG/redb の baseline copy とも同じ更新 algorithm ではない。`report.md:15,29,65` も比較限界を認める。数値差そのものを選定の hard correctness gate にしない。

## 判定の境界と次の exact action

- **今受け入れること:** PostgreSQL incidence を最初に追加検証する暫定方針、三方式の小規模 n-ary payload 格納、relation-only update、reported offline restore の成立可能性。PG の同一 DB transaction 適合は設計上の利点であって READY/pointer/pin/GC 実装済みという意味ではない。
- **今進めないこと:** `P3-P04 Selected`、`P3-G03` の production backend 依存・migration、`spec/selection/library-tool-selection-v0.md:567` の **POC REQUIRED** 更新、P3/P7 runtime qualification 完了宣言。Neo4j Community は [公式に GPLv3](https://neo4j.com/open-source-project/) で、[Community dump は offline](https://neo4j.com/docs/operations-manual/current/backup-restore/offline-backup/)。製品採用には別の法務・運用適格性が必要であり、本 PoC はその承認ではない。
- **選定前の bounded 追加 PoC:** 既存 fixture を活用し、Source 1/2 で同じ裸 ID に異なる current access を与える case、retention 拒否、owner spoof、負 offset と NULL/空値、same-ID participant/qualifier 変更を追加する。各 backend で persisted participant/incidence と relation payload を再構成・相互検証し、期待値を実 memory oracle から固定した query と全 relation/content digest に比較する。少なくとも high-degree/multi-hop/visible budget の限定 case と一つの現在 access error case を含める。計画との差分を明示的に改訂するか残余を `UNMEASURED` として `Blocked` にする。
- **P3-P04 証拠を閉じること:** 同一 fixture hash と measurement phase を記録した machine-readable qualification report、raw samples、各候補の実行/復旧 transcript、version/image digest、容量・予算結果、fail/skip 理由、事前固定した選定判定を保存する。Neo4j は Bolt `neo4rs` の計画を実行するか HTTP への変更を承認済み計画に反映する。候補比較と fault canary を再評価し、PG を選ぶなら独立 review 後に selection receipt を記録する。
- **その後の別 gate:** PG production migration/DB roles/READY mutation trigger/canonical digest/owner binding、build guard と P7 の単一 pointer・lease・GC を実 DB の lock 順と crash/restore で検証する（`p3-graph-plan.md:115-205`）。さらに P7 multi-index runtime、HTTP、exact-head hosted gates は別 receipt。今回の isolated PoC にこれらの production 完了を要求して NO-GO としたわけではなく、P3-P04 自身の不足を判定した。

確認方法: 上記 source、fixture JSON、report、lockfile、freeze/plan を read-only で照合し、SHA-256 と JSON case 件数を再計算した。Docker container の再作成、大規模再 benchmark、backup restore の再実行は行っていない。
