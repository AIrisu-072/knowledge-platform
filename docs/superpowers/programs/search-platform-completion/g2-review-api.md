Findings:
- [P2] crates/search-runtime/src/api.rs:572 - The final disclosure gate never checks `disclosed_fields.claims`. It returns Ok as soon as `resources` is empty, and the per-item loop covers only Resources, even though the backend holds the actor-visible Claim catalog (`self.claims`) and `with_disclosure` fills `claims` for Discover (remote_disclosure.rs). - A Claim whose visibility to the actor is withdrawn after the Discovery evaluation closes but before the gate runs is still sent: its ClaimId and state go out in the 200 body. A Discover result with Claims but no qualified Resources skips every item/field recheck after the actor/Source check. The earlier "gate ignores DisclosedFields" fix is therefore incomplete. - Recheck every disclosed ClaimId against the actor-visible Claim catalog (fail-closed on error or Unknown) before returning Ok, and drop the early return so it does not skip the Claim check.
- [P3] crates/search-runtime/src/api.rs:586 - The gate looks up each Resource's owning Source with `.find(|(id, _)| id == resource)`, so only the first (ResourceId, SourceId) pair is ever checked. - If one result has the same ResourceId from a Remote Source and from a Document Source, with the Remote pair first, both iterations take the `Remote(_) => {}` arm, so the Document item's current-access recheck never runs. A remote provider that controls the IDs it emits can arrange this. - Iterate over `resource_sources` pairs (deduplicated) and recheck each one, and also refuse any `resources` entry that has no pair.
- [P3] crates/search-runtime/src/api.rs:223 - `operation_timeout` is checked only for zero; it has no upper bound. The router then computes `Instant::now() + state.timeout` for every authenticated request. - A host that sets a very large timeout (e.g. Duration::MAX as "no limit") passes startup, but every authenticated request panics on Instant overflow in the handler instead of getting a Problem response. - Refuse startup above a fixed maximum operation timeout, or use `checked_add` and map overflow to a startup error.
- [P3] crates/search-runtime/src/api.rs:434 - The host `DiscoveryConfig` is first validated per request: `DiscoveryService::new(...)` failure maps to ServiceUnavailable, while startup never builds or validates it. - An invalid DiscoveryConfig lets the runtime start, then every /v1/search request returns 503, which contradicts the factory's "refuse startup unless every input is wired" contract. - Validate `host_config.config` in build_search_api_runtime, before the ledger is touched, and return a StartupError.
