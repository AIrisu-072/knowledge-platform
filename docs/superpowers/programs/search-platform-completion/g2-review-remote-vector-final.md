# G2 re-review: remote HTTP Source adapter, guarded transport, Vector contract

Scope (read-only): crates/search-source-http/src/transport.rs, crates/search-source-http/src/adapter.rs, crates/search-application/src/remote_evidence.rs, crates/search-application/src/vector.rs. Line numbers were counted in the content as read.

Re-review of prior findings:
- Provenance lookup asks /authorize first: FIXED - crates/search-source-http/src/adapter.rs:559-563. `lookup` asks `authorize` for the actor and the pinned identity and returns `None` unless the answer is `Allowed`. It does this after the scope filter at adapter.rs:554-558 and before the content fetch at adapter.rs:564.
- Version/digest of looked-up content vs the pinned target: NOT A DEFECT - crates/search-application/src/remote_evidence.rs:195-199. `verify_provenance` rejects the record unless both `record.version` and `record.digest` equal the pinned target's. The adapter fills them from the current content (adapter.rs:577-578), so a drifted item cannot verify.
- Lookup failures as Ok(None): NOT A DEFECT - crates/search-application/src/remote_evidence.rs:127-128 documents `None` as "unverified, Claim unknown", and verify_provenance maps it to `Ok(None)` at remote_evidence.rs:192-194. This fails closed and never counts as absence.
- Evaluation eviction: FIXED - crates/search-source-http/src/adapter.rs:152-156. A new evaluation at capacity is refused (`None`, so the budgeted call becomes `Unavailable` at adapter.rs:183-186), and no running entry is evicted.
- Entries outliving an evaluation: NOT A DEFECT within the listed sources (mitigation unverified). Nothing ever removes entries from `evaluations` (adapter.rs:101, 157-161). The per-request production factory that drops the adapter is not in the listed sources, so I could not confirm it here. The `'a` borrows of the authority and visibility ports (adapter.rs:96-101) suit a short-lived adapter. Current access is always re-asked of /authorize (adapter.rs:422-427), so a stale entry only supplies an identity to ask about. The residual risk is recorded as P3 below.
- current_policy order and scope: FIXED - crates/search-source-http/src/adapter.rs:441-443. The registration and scope check comes before anything is sent. The single-kind check (adapter.rs:446-448) also comes before the actor's principal goes to /authorize (adapter.rs:450).
- resource_kind: FIXED - crates/search-source-http/src/adapter.rs:446-449. Only a registration with exactly one allowed kind answers; any other returns `SourceUnavailable`.
- Dot-segment path traversal: FIXED - crates/search-source-http/src/transport.rs:283-290. `.` is left unencoded by `encode` (transport.rs:114), but any `.`/`..` segment normalized by `join` changes `url.path()`, so it fails `url.path() != expected_path` and becomes `Endpoint`. `%` is always re-encoded (transport.rs:117), so `%2e` cannot be decoded into a dot segment. A `//host` base path is caught by the host check at transport.rs:284.
- rank_list when unavailable: FIXED - crates/search-application/src/vector.rs:359-361. It returns `None` whenever the batch is unavailable, and `generation` is `None` for `VectorRetrievalBatch::unavailable()` (vector.rs:328).
- Forgeable Vector activation: FIXED - crates/search-application/src/vector.rs:73-75, 78-88, 99. `TrustedVectorQuery::compile` takes policy and model only from the host `VectorActivationPort`. `build` checks the same registered model (vector.rs:530-533), and `retrieve` binds the provider spec to the compiled model id (vector.rs:398-402).
- Purge vs publish race: FIXED for builds in flight - crates/search-application/src/vector.rs:534-537, 609-616, 663-673. `purge` advances the scope epoch before withdrawing and purging, and `publish_if_current` is a CAS on that epoch, so a build that read the epoch before the purge loses the CAS and discards its stage. A narrow residual window remains: the epoch is sampled inside `build`, not together with the caller's input. That is recorded as P3 below.

Fresh review (SSRF, fail-open, identity/retention leaks, unbounded resources, contract violations):
- SSRF: no defect found. IP-literal hosts are rejected (transport.rs:235), and a numeric host the URL parser rewrites is caught by the host re-check at transport.rs:245. Every resolved address must be public and on the registered port (transport.rs:314-321), and the checked addresses are pinned per call with a fresh, unpooled client (transport.rs:324-334). There are also no proxies, redirects or retries, and HTTPS is required in production (transport.rs:211).
- Fail-open: no defect found. Transport, status, budget and decode failures all map to `Unknown` outcomes (adapter.rs:76-86, 226-234). Denied or not-current Vector hits are suppressed, and Unknown makes the batch unavailable (vector.rs:290-312, 460).
- Unbounded resources: response bytes are capped on both Content-Length and decoded chunks. List and content requests are capped per evaluation, and tracked evaluations are capped at 256. /authorize calls are deliberately unbudgeted (adapter.rs:352), but each one is driven by a bounded set of observed candidates.

Findings:
- [P3] crates/search-application/src/vector.rs:534-537 - The scope epoch the publish CAS compares against is read inside `build`, after the caller has already captured `input`. A purge that completes between the caller reading the `VectorManifestInput` and line 534 is not seen. Scenario: an authority scope is revoked and `purge` (vector.rs:663-673) advances the epoch and purges the index. A build that was handed the pre-revocation input then reads the new epoch, stages the revoked scope's embeddings and publishes them. If the P1 bundle key did not change, the embeddings are retained past revocation. Query-time `resolve_hit` should still suppress the hits, so this is a retention leak, not a disclosure. Suggested fix: read the epoch together with the P1 input and carry it on `VectorManifestInput`, or have the caller pass it in.
- [P3] crates/search-application/src/vector.rs:579-582, 609-612 - `?` on `index.stage` and on `publish_if_current` returns without discarding the stage, even though the module doc (vector.rs:14-15) promises that the unpublished stage is discarded. Scenario: the generation store times out during the CAS. The fully staged embeddings stay in the index until the next restart's `recover`, or a `purge_scope` of that scope. Suggested fix: on an Err from `publish_if_current`, discard the descriptor (best effort, as at vector.rs:586) before returning. Also have the index port clean up a partial `stage` on failure.
- [P3] crates/search-source-http/src/adapter.rs:101, 154-161 - Evaluation entries are never removed. They keep each actor's `TrustedRemoteContext` and observed native IDs for the adapter's whole lifetime, and after 256 evaluations every new one is refused. Scenario: a host keeps one adapter across requests instead of using the per-request factory. Actor identities and item IDs are retained indefinitely, and after 256 evaluations every list/content call is `Unknown(Unavailable)`. Suggested fix: add an explicit `finish_evaluation(id)` (or a drop-scoped guard) that removes the entry. Alternatively, enforce the per-request lifetime in the type, e.g. by making the adapter non-reusable across evaluations.
- [P3] crates/search-source-http/src/adapter.rs:116-126 - `HttpRemoteSourceAdapter::new` checks that the transport's limits fit the registration, but not that the transport was built for this registration's endpoint. Scenario: a host miswires a transport for registration A into the adapter for registration B. All `owns` checks pass, and B's actor principals (adapter.rs:348) and queries are sent to A's origin. Suggested fix: keep the `RegisteredEndpoint` in `GuardedHttpTransport` and require it to equal `registration.endpoint()` in `new`.
- [P3] crates/search-source-http/src/adapter.rs:477-481 - `probe_or_materialize` fetches and decodes the item's full content for the actor's context without asking /authorize first. This is unlike `lookup` (adapter.rs:559-563) and `current_policy` (adapter.rs:450-455). It then returns the item's current version/digest. Scenario: the actor's item access was revoked after the search. A probe still pulls the body over the wire, uses up the content budget and reports the current version/digest to the caller. Correctness depends on every caller having gated on `current_policy` first. Suggested fix: require an `Allowed` /authorize answer for `target.identity()` before the content call, as `lookup` does.
- [P3] crates/search-application/src/remote_evidence.rs:200-211 - The comment says the role of a direct record comes from the record ("a direct record may only say it corroborates or contradicts"). The code instead takes it from the untrusted `hint.role_label`, and `VerifiedSourceProvenance` has no role field. Scenario: a search response labels a directly verified record as "contradicting". The Claim then gets contradicting evidence whose polarity the provenance lookup never verified. Suggested fix: add a role or polarity field to `VerifiedSourceProvenance`, decoded from the lookup, and take it from the record. Otherwise default to `Primary` and ignore the hint.
