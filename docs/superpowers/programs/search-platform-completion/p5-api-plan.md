# P5 Full Search API Implementation Plan

> **For agentic workers:** `superpowers:subagent-driven-development` または `superpowers:executing-plans` を task 単位で適用する。実行 controller は repository の `orchestrate` / `toolbox-context` 契約、指定モデル `gpt-6-sol/max`、独立 read-only review を優先し、native worker への切替は理由と境界を記録する。本書は計画であり code/SQL/HTTP/CI の受入記録ではない。

**Goal:** 同じ trusted actor、P4 の一つの可視 Source catalog と Search Application を通る四つの HTTP operation を実装し、Document 実 DB/FS と Remote 実 local TCP で wire と開示寿命を検証する。

**Architecture:** `search-api-http` は認証済み opaque handle、公開 DTO、Problem、送信寿命だけを持つ。`search-application` は P4 の `TrustedSearchScope` / `AuthorizedSourceScope` / `ScopedSourceRegistryPort` と既存 routing/retrieval/S1/Discovery evaluator を再利用する。Source-owned Document/Remote adapter と durable owner/current/pin は `search-runtime` の composition root で配線する。

**Tech Stack:** Rust 1.98/edition 2024。選定済み axum 0.8.x、tower 0.5.x、tower-http 0.7.x、serde/serde_json、Tokio、OpenAPI 3.2.1、Redocly CLI 2.x、必要な schema 試験に選定済み jsonschema 0.55.x。HTTP ref の実績値は axum `=0.8.9` / tower `=0.5.3` / tower-http `=0.7.1`。現 checkout の `Cargo.lock` は axum/tower を含むが `search-api-http` は未作成なので、root/lock 変更は一人の integration writer が固定する。`axum::serve` の body 送出通知を handler 完了と混同しない（[axum serve](https://docs.rs/axum/0.8.9/axum/fn.serve.html)、[Body](https://docs.rs/axum/0.8.9/axum/body/struct.Body.html)）。

**Spec:** `p5-api-freeze.md` → `p5-api-contract-revision-2.md` → `p5-api-contract-reconciliation.md` → `p5-api-design-revision-1.md` → `p5-api-design.md` の優先順。P1/P3/P4 の各 freeze と P1 Archive binding ruling を継承し、`spec/` を normative SSOT とする。

- [ ] RED: `spec/api/openapi.yaml` に四 path がなく、`spec/errors/search-api-error-registry.yaml` がないことを記録する。四 operation の `200` と 400/401/403/404/409/413/415/422/429/431/503/504 の**適用対象**、security scheme と 401 header、success/Problem header を期待する schema fixture を先に定義する。
- [ ] GREEN: Search §15 に `about:blank`、status と固定 reason `title`、宣言済み `code` extension、固定 `detail`、`trace_id`、`instance` 省略、`Content-Type: application/problem+json`、全 Problem の `Cache-Control: private, no-store` / `X-Content-Type-Options: nosniff` を追加する。registry に 400 `MALFORMED_REQUEST`、401 `AUTHENTICATION_REQUIRED`、403 `FORBIDDEN`、404 `RESOURCE_NOT_FOUND`、409 `CURSOR_STALE`、413 `PAYLOAD_TOO_LARGE`、415 `UNSUPPORTED_MEDIA_TYPE`、422 `VALIDATION_FAILED`、429 `RATE_LIMITED`、431 `REQUEST_HEADERS_TOO_LARGE`、503 `IDENTITY_UNAVAILABLE` / `DEPENDENCY_UNAVAILABLE` / `SERVICE_UNAVAILABLE`、504 `UPSTREAM_TIMEOUT` を固定し、503 内部 deadline の detail は `The service could not complete the operation.`、504 実 upstream wait は `An upstream service did not respond in time.` とする。他の detail は照合追補 §5 の固定表に従う。`WWW-Authenticate` は実配線 scheme の challenge だけを 401 に必須化し、`Retry-After` / `retryable` は公開 retry policy が安全に確定した場合だけ付ける。
- [ ] GREEN: v0 の実配線 scheme を HTTP Bearer として `Authorization: Bearer <opaque token>` を `SearchCredentialVerifierPort` が検証し、401 challenge を固定 `Bearer realm="search"` にする。四 operation の OAS `securitySchemes` は `type: http, scheme: bearer`、operation security と 401 `WWW-Authenticate` header を同じ binding に揃える（[OAS 3.2.1 §4.27](https://spec.openapis.org/oas/v3.2.1.html#security-scheme-object)、[RFC 9110 §15.5.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.2)）。fixture token は server 側だけで既知 descriptor へ解決し、production は host verifier がないと起動しない。将来 scheme を変える場合は Search 規範/OAS/handler の明示差分と再試験が先。`pnpm api:lint` / `mise run api:check` が PASS、Document 既存 path/schema の差分が無いことを確認する。[Redocly bundle](https://redocly.com/docs/cli/commands/bundle/) の JSON bundle を後続 parity test の固定入力にする。
