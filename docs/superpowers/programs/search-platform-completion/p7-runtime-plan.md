## 3. W1/W2 の mandatory acceptance

**W1 — `document.version.read_confirmed`。** `spec/operations/observability-audit-requirements-v0.md:540–597` に従い、初回明示的既読確認を必須 Audit class として R04A-S の class policy・Document legacy decoder、R04A-D の sink projection に含める。Document owner は既存 `crates/document-repository-postgres/src/read_state.rs:146–164` の producer を、`tests/read_state_transaction.rs` 等の実 PG で class 固有に検証する。`read_confirmed_audit_insert_failure_rolls_back_first_read` を RED→GREEN とし、Audit INSERT failure 時に初回既読 state が commit されず、成功応答も出ず、Audit row も残らないことを別接続で確認する。重複確認を初回 event として二重生成しない。R04A-S/D は decoder/class 許可と sink 投影、Document owner は business rollback、R09 は両 receipt を照合する。その他 Document 必須 class と P5/R05/R03 の class 別 rollback/拒否試験も省かない。

**W2 — 全 file が存在する fresh DB bootstrap。** R03 は migration/admission integration の owner、R09 は独立受入 owner として、fresh disposable PostgreSQL に Domain `0009` → Search `0001`〜`0003` → Domain `0010` → Search `0004` の順を実際に適用・観測する。Search `0005` はその後、R05 に従う。Domain `_sqlx_migrations` と Search `search_runtime_sqlx_migrations` の version/checksum を段階ごとに照合し、migrator、Audit append/dispatcher、host inventory publisher/reader、Source registration、API/claim の実接続 role/grant と過大権限拒否を確認する。`fresh_bootstrap_domain_search_audit_inventory_order` と `fresh_bootstrap_rejects_checksum_or_role_mismatch` を RED→GREEN にする。現行 `search-runtime::migrate` は単一 `sqlx::migrate!("./migrations")` 入口なので、全 migration file が揃った状態の呼出しだけを所定の段階順の証拠にしない。順序を保証する起動/移行手順を限定 writer window で実装し、逆順・欠落・checksum drift・role 不一致なら listener/claim/readiness を閉じる。本番 migration の実行資格ではない。

## 4. Completion boundary と次の exact action

五つの architecture 指摘は設計上閉じたが、上表の試験は未実行である。最初に R04A-S と P7-03 の schema/role gate、および R01 trusted input を実装受入し、次に R01P の実 publisher と Audit failure/unknown commit の負試験へ進む。R02 は実 publisher/ledger/current/scan が揃ってから組み立て、R03/R09 は W2 を fresh DB で判定する。各 producer は W1 を含む class 別同一 transaction・rollback を所有者の試験で証明する。R04P の採択、P3-P04 backend selection、P2 Vector/runtime mode、P1〜P6 final receipt が未達なら R06/R09 の該当 production gate を閉じたままにする。

R09 の最終判断まで、production readiness、SLO 保証、merge、本番 migration、live deployment を宣言しない。失敗や不明な資格は元 owner の focused 修正と独立再 review に戻す。
