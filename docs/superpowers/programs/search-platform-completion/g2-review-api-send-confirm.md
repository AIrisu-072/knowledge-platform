Regression checks:
- Shutdown still closes every lease. Any registry still referenced by a task stays in `active` (crates/search-api-http/src/send.rs:252) and is closed with `Cancelled` before the tasks are aborted (crates/search-api-http/src/send.rs:276-279). A registry is only removed from `active` once `active` holds the last reference. Dropping it at that point runs `Registry::drop`, which closes any lease still open with `Dropped` (crates/search-api-http/src/send.rs:98-106).
- A completed response still closes its lease exactly once. `close_all(reason)` runs when the connection future ends (crates/search-api-http/src/send.rs:265-270). `SendLease::close` returns early once the lease is closed (crates/search-api-http/src/send.rs:72-74), so a later `Cancelled` or `Dropped` close does nothing and the observer sees one `closed` event.
- No new fail-open in the changed code. An internal timeout, an open evaluation, an oversized body or a gate refusal all produce a 503 problem response with no body bytes.

Findings:
- [P3] crates/search-api-http/src/router.rs:330 - the backend deadline is computed after the body read and credential verification, but the outer timeout started at crates/search-api-http/src/router.rs:218. The deadline passed to `authenticate` is therefore later than the deadline that actually applies. - Scenario: a slow client upload or a slow verifier uses 4 s of a 5 s timeout. The backend still sees about 5 s of budget, plans a remote wait it cannot finish, and the outer timeout cancels it mid-flight. The client gets a generic 503 instead of the backend's own deadline result (for example a real upstream 504). - Fix: capture `let deadline = Instant::now() + state.timeout;` at the start of `route`, use `tokio::time::timeout_at(deadline.into(), ..)` for the outer bound, and pass that same `deadline` into `pipeline` and `authenticate`.
- [P3] crates/search-api-http/src/send.rs:252 - `active` is only pruned when a new connection is accepted. If a connection task panics, `leases.close_all(reason)` at crates/search-api-http/src/send.rs:270 never runs, and `active` still holds the registry, so `Registry::drop` cannot run either. - Scenario: a handler panics during a send. Its `SendLease` stays open with no reason recorded, and the observer gets no `closed` event, until another connection is accepted or the server shuts down. Telemetry briefly shows a disclosure lease open for a connection that no longer exists, and it is finally reported as `Dropped` rather than `ConnectionError`. - Fix: close the leases from a drop guard inside the spawned task, e.g. a guard whose `Drop` calls `close_all(CloseReason::ConnectionError)` unless it was disarmed after the normal `close_all`. Alternatively, prune `active` in the `join_next` arm at crates/search-api-http/src/send.rs:241 as well as on accept.
- [P3] crates/search-api-http/src/router.rs:230-232 - when a request carries no `ConnectionLeases` extension, the success path sends the disclosed bytes through `success()` with no `SendLease` and no `Connection: close`. `SearchApiRuntime::router()` (crates/search-runtime/src/api.rs:184-186) is public and does not require that `send::serve` is the transport. - Scenario: a host serves the runtime router with `axum::serve`. Every 200 is then sent untracked by any disclosure lease, over a keep-alive connection, and the observer never sees `opened` or `closed`. - Fix: return 503 when `ConnectionLeases` is missing, except under an explicit test-only constructor. Or have `SearchApiRuntime` expose a `serve` that wraps `send::serve` instead of handing out the bare `Router`.
