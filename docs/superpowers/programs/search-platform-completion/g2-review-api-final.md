Findings:
- [P2] crates/search-api-http/src/send.rs:234 - The production socket server spawns one JoinSet task per connection (send.rs:249). It never reaps completed tasks: the accept loop at send.rs:237-268 does not call join_next or try_join_next, so finished tasks stay in the set until shutdown. Each connection serves exactly one response with keep-alive off (send.rs:256-258), so this leaks one task allocation, sized to the connection future, per request. Failure: a long-running API node serving many millions of requests grows memory without bound and is eventually OOM-killed, taking every in-flight response with it. Suggested fix: in the select! loop, drain finished tasks with `while connections.try_join_next().is_some() {}` or add a `Some(_) = connections.join_next()` arm. Also cap concurrent connections with a semaphore, because accept currently has no concurrency limit either.
- [P3] crates/search-api-http/src/router.rs:154 - build_search_router is public and rejects only a zero operation_timeout. pipeline then computes `Instant::now() + state.timeout` (router.rs:331), which panics on overflow when the duration is huge. Failure: a host that wires the router directly, without build_search_api_runtime, with something like Duration::MAX panics in every authenticated request handler. Suggested fix: move the MAX_OPERATION_TIMEOUT bound into build_search_router, or use Instant::checked_add and fail at startup.
- [P3] crates/search-api-http/src/router.rs:214 - The POST body is read (to_bytes at router.rs:249) before the operation-deadline timeout starts at router.rs:217. The module doc at router.rs:7-8 says the whole pipeline runs under the operation deadline, but body reading does not. Failure: outside send.rs serve, whose send_deadline bounds the whole connection, a slow-body client holds a handler for as long as the transport allows. Suggested fix: wrap bounded_body in the same tokio::time::timeout(state.timeout, ...) as the pipeline.
- [P3] crates/search-runtime/src/api.rs:626 - The final gate skips per-item rechecks for Remote-owned items because the evaluation is assumed closed. Nothing enforces that assumption: router.rs:363 reads disclosure.evaluation_closed() only to report it to the lease observer (router.rs:231-232), and still discloses when it is false. Failure: if a remote evaluation view ever fails to close (remote_disclosure.rs evaluate returns view.is_closed() as false), remote items are disclosed with neither a closed evaluation nor an item recheck, which fails open. Suggested fix: refuse disclosure (503) when evaluation_closed() is false, either in the pipeline before disclose_with/with_disclosure or inside the runtime gate when the owner includes Remote Sources.
- [P3] crates/search-api-http/src/send.rs:241 - When listener.accept() returns an error (for example EMFILE or ENFILE under descriptor exhaustion), the loop continues straight to the next accept, with no backoff. Failure: under fd exhaustion the accept loop spins at 100% CPU and starves the in-flight connections that would free descriptors. Suggested fix: sleep briefly on accept errors, and bound concurrent connections (see the P2 above).
- [P3] crates/search-runtime/src/api.rs:264 - Remaining recorded finding: DiscoveryConfig is not validated at startup (see above). Failure: a misconfigured DiscoveryConfig starts cleanly, then answers every Search and Discover request with 503. Suggested fix: construct and validate the config once in build_search_api_runtime and add a StartupError variant for an invalid config.
