Findings:
- [P2] crates/search-source-document/src/extraction.rs:312 - The pre-admission size check only runs when `admission_limit` returns `Some`. It returns `None`, and the check is skipped, in three cases: the declared media type is outside `declared_format` (extraction.rs:169), the format has no registered definition, or the definition has no `InputBytes` limit (the `?` at extraction.rs:173). `read_raw` (extraction.rs:321) then reads and hashes the whole object into memory, bounded only by its declared size, before `detect` (extraction.rs:322) classifies it as `Unsupported`. That outcome needs no bytes at all. - Failure scenario: a Document Source holds a multi-GB `video/mp4` or ISO image. Every body build, and every retry, buffers the whole object in a `Vec` and hashes it before recording `Unsupported(UnsupportedFormat)`. A few such items running in parallel can exhaust the indexer's memory. This is the same resource-exhaustion problem the prior finding was about. - Suggested fix: in `extract_item`, return `ExtractedItemResult::unsupported(None, None, CoverageReason::UnsupportedFormat)` before any read when `declared_format(..)` is `None` or the registry has no definition for that format. Also make `BodyProfileRegistry::new` (extraction.rs:120) reject any definition that has no `InputBytes` limit, so admission can never be skipped silently.
