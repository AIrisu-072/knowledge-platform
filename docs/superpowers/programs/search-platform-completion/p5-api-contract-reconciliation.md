## 1. 共通 trusted scope は P4 の型を一つだけ使う

| P5 改訂 1 の概念 | この照合で固定する唯一の application 境界 | 入口と利用 |
| --- | --- | --- |
| `TrustedSearchContext` | **request-local wrapper** `SearchOperationContext { actor: TrustedSearchScope, operation_deadline, cancellation }`。`TrustedSearchScope` 自体は P4 の型を再利用する。 | composition root が設定した `VerifiedActorResolverPort` を `CheckedAuthorityAdapter` に注入し、検証済み opaque handle から scope を得る。wrapper は scope の tenant/principal/session/access revision を再 mint・変更しない。operation deadline は trusted scope の期限以下。 |
| `AuthorizedSourceSet` | P4 `ScopedSourceRegistryPort::visible_sources(&TrustedSearchScope)` が返す `VisibleSourceRegistration` と各 `AuthorizedSourceScope` の request-local **view**。 | actor と同じ tenant、現行 registration/activation・visibility revision、全 tenant 横断で一意な server-owned `SourceId` を検証し、可視集合を routing 前に確定する。別の Source 許可集合の constructor を作らない。 |
| `ActorVisibleSourceRegistryPort` | **別 port は採らない**。P4 `ScopedSourceRegistryPort`、`CurrentSourceVisibilityPort`、`CheckedSourceVisibilityAdapter` を使う。 | `check_actor_current` → complete visible catalog → Source scope `current` を共通処理にする。P4 の `prepare_visible_sources` は Discovery binding 用の現行 helper であり、他の三 route に架空の Discovery evaluation を作らず、同じ actor/registry/scope 検査を operation 共通 helper に抽出する。 |

`VerifiedActorResolverPort` は server 設定の信頼境界である。合成 `SyntheticAuthorityAdapter` は in-process harness 専用とし、HTTP caller が resolver、`VerifiedActorDescriptor`、tenant、principal、role、group、subjects、`InvocationKind`、service executor、access handle、Source grant を選べない。実 transport の identity adapter が検証した opaque session handle をこの resolver へ渡す。`CheckedAuthorityAdapter::authenticate_handle` の文字列検査だけを認証の証拠にしない。session が tenant を一意に決められない場合、registry 前に失敗する。identity/visibility port 未配線の composition root は四 route の起動を拒否する。OpenAPI security scheme は実際に配線した transport の証拠で定め、bearer/cookie/mTLS の架空の scheme を先書きしない。

現在の `VisibleSourceRegistration` は remote registration を内包する。P5/P7 では同じ `AuthorizedSourceScope` を local Document Source にも渡せる source-neutral な scoped catalog view が必要である。拡張しても新しい mint/visibility decision を足さない。P4 trust 修正で予定する `SourceRegistrationLedgerPort` の atomic `reconcile/current` 契約に従い、composition root は **host-configured durable Source ownership ledger** で過去の `(SourceId, tenant owner)` と既存 `(SourceId, generation)` を再起動後にも照合し、登録・更新を原子的に検査する。現在の in-memory `RemoteRegistrationCatalog.history` だけでは全 tenant 横断一意を保証しない。ledger 未配線の production factory は四 route の起動を拒否する。P7 の実 PostgreSQL adapter は後続実装であり、この文書の時点で接続済みとはしない。`DiscoveryRequest.access_context: String` への互換変換は scope 内部の opaque 値に限定し、公開 request や provider JSON に許さない。

P4 code review の P2-2/3 に従い、`CurrentSourceVisibilityPort::current(&AuthorizedSourceScope)` は可視 grant だけでなく `SourceRegistrationLedgerPort::current` の **現行 durable owner・現行 registration・activation epoch/tombstone・registration revision・visibility revision** を毎回検査する。登録削除または取消は単調な tombstone/activation epoch を残し、同じ registration/visibility revision で再追加しても old scope を復活させない。個別 Source の `Denied`/`Unknown` は可視集合から除外し、他の許可済み Source を列挙できる。actor/registry/ledger/visibility 基盤の error で complete snapshot を作れない場合だけ四 route を generic 503 で fail closed にする。P4-07 の全 read/write と P5 final gate もこの **同じ** current gate を通す。

四 route の順序は `trusted identity/tenant/operation authorization → actor-visible Source snapshot → 公開 selector と可視集合の交差または可視 locator → routing/pin/provider I/O → item/field/Graph participant の current final gate → safe DTO` とする。`ScopedSourceRegistryPort` の失敗で完全な可視 snapshot を作れない場合は 503 の generic Problem で止め、隠れた Source の稼働確認・失敗数を使って partial を組み立てない。

| route | visibility より後にだけ許す lookup と漏洩防止 |
| --- | --- |
| `POST /v1/search` | `sourceIds` は可視 Source との intersection。未知・他 tenant・不可視 ID は同じ空 intersection で、unknown count、gap、trace、`partial` の差を作らない。可視 scope だけで route、pin、retriever、S1 fuse する。 |
| `POST /v1/discover` | `requiredClaimIds` は構文・個数だけを先に検査。可視 Claim binding、必要 Source、P1 の body scope を可視集合の内側で確定してから route する。不可視・未知 Claim を落として残りだけで `Sufficient` にしない。 |
| `GET /v1/resources/{resourceId}` | `(TrustedSearchScope, AuthorizedSourceScope, ResourceId)` の範囲で Source-owned visible locator を引く。裸の global ID、provider locator、Graph hit から Source を決めない。未知・他 tenant・不可視・旧版・T10 終了・曖昧 mapping は同じ 404 body/header/cache policy。live/current だけで history fallback はない。 |
| `GET /v1/sources` | 完全な actor-visible catalog から安全な capability summary のみ作る。page 送出直前に Source existence を再検査し、可視集合 stamp/digest が変わった継続は `CURSOR_STALE`。registry 障害から部分一覧を 200 にしない。 |

公開 input は `SearchQuery` の `query`、`resourceTypes`、`sourceIds`、`coverage`、`pageSize`、`cursor`、`DiscoveryInput` の `need.{purpose,requiredResourceTypes,requiredClaimIds,temporalTarget?,businessTimezone?}`、`query?`、`coverage`、SourcePage の `pageSize`/`cursor`、GET の canonical `resourceId` だけとする。`current_access`、trusted context、tenant/actor/role、routing、evidence requirement、provider permission、retention、generation、selector predicate/value は server が派生し、未知 JSON field は拒否する。公開 `temporalTarget` は history 権限ではない。

## 2. P1〜P4 と Core の成功 wire 写像

次表の field 名は lower camel case の公開 DTO。`search-core` の `Serialize` 導出をそのまま HTTP に使わず、source/item/field の final grant 後に private projection で構築する。`ResourceKind`、`ApplicabilityState`、`EvidenceSufficiency` 等は明示した wire enum へ写像し、Rust `Debug` 文字列や自由文字列を契約にしない。

| 公開 DTO | 凍結入力・現行 Core からの写像 | safe field と enum／遮断 field |
| --- | --- | --- |
| `SearchPage` | P1 `BodySearchSpec` / `KnowledgeUnitHitRef`、P4 scoped Source、現行 `FederatedCandidate`・`CandidateFederator::PriorityConcat`。 | `items[]`, `nextCursor`, `partial`, `coverage[]`, `gaps[]`, `traceId`。item は現在許可された `resourceId`,`sourceId`,`resourceType`,`resourceVersionId?`,`title?`,`rank`,`matchedFields[]`,`snippet?`,`provenance` のみ。`coverage` request enum は `titleAndPermittedMetadata` / `bodyRequired`、response `coverage[].kind` は `titleAndPermittedMetadata` / `bodySearchWithPerItemCoverage`。snippet field/coverage は許可された `title` / `metadata` / `body`。`candidate_id`、locator、raw score、retrieval trace ref は出さない。 |
| `DiscoveryEvaluation` | `DiscoveryResult`、`QualifiedResource`、`Claim`、`EvidenceSufficiency` を同一 generation・current grant で縮約。 | `needId`,`discoveryEvaluationId`,`qualifiedResources[]`,`evidenceSufficiency`,`evidence[]`,`gaps[]`,`rejectedCandidates[]`,`evaluationCompleteness`,`completenessReasonCodes[]`,`trace[]`,`traceId`。`evidenceSufficiency` は `sufficient` / `insufficient` / `unresolved` / `conflicted` / `invalid`。qualified item は許可済み `resourceId`,`sourceId`,`usageProfileId?`,`applicability`,`matchedConditionCodes[]`,`resolvedDiscriminatorCodes[]`,`evidenceIds[]` に限り、`applicability` は `applicable` / `excluded` / `unresolved` / `invalid`。内部 `qualification_trace`、任意の condition 文や contrast 文は出さない。 |

`resourceType` の wire enum は現行 `ResourceKind` の `knowledge`,`document`,`folderPlacement`,`semantic`,`capability`,`agentSkill`,`workflow`,`policy` だけ。`bodySearchWithPerItemCoverage` は本文検索 port が実接続されたという能力表示に限り、Source 全体・全 item の本文完全性を意味しない。個々の P1 `Supported` / `Partial` / `Unsupported` / failure と現在の Read から結果と blocking gap を決める。snippet は Source が field 開示を許した plain text 最大 320 Unicode code points と field/coverage code だけで、HTML や raw locator は含めない。現在の `QualifiedResource` には SourceId がないため、`sourceId` は同一 key の認可済み候補・projection binding から付け、裸 ID で逆引きしない。Source 単位の routing と retriever 優先順を維持する **S1 `PriorityConcat`** であり、raw score の cross-Source 比較、公開 score、別の fusion policy を導入しない。最終 gate で消えた item から rank、count、gap/trace を再計算し、page 継続 key もその順序と一致させる。

現行 `GapReason` 八種には `PAGINATION_UNAVAILABLE`、opaque な required Claim/Source failure、budget reason がない。P5/P4 の Application 側に閉じた `PublicGapReasonCode` の追加 variant `PAGINATION_UNAVAILABLE`,`REQUIRED_CLAIM_UNRESOLVED`,`REQUIRED_SOURCE_UNAVAILABLE`,`BUDGET_EXHAUSTED` を型付きで定義し、Core の既存 `MissingFact` に偽装しない。`evaluationCompleteness` は `complete` / `bounded` / `interrupted` とし、追加 `EvaluationCompletenessReasonCode` は `BUDGET_EXHAUSTED`,`SOURCE_INTERRUPTED`,`REQUIRED_EVIDENCE_UNEVALUATED`,`BODY_COVERAGE_INCOMPLETE` に限定する。`completenessReasonCodes[]` はこの enum のみ。実行済み optional action の障害は可視 Source に限る `AVAILABILITY` と `interrupted`、上限到達は `BUDGET_EXHAUSTED` と `bounded`、required evidence 未評価は blocking gap と `REQUIRED_EVIDENCE_UNEVALUATED` を返す。情報が欠けても安全な独立結果と最終 gate を確定できた場合だけ 200 とし、required evidence の欠落を `sufficient` にしない。確定不能なら 503/504 Problem のみ。SourcePage と ResourceDetail は partial 成功を持たない。

`requiredClaimIds` の ID namespace は source-owned catalog が定義し、HTTP は UUID の形式と 1〜16 件という公開制限のみを見る。P5 改訂 1 の `ActorVisibleClaimCatalogPort` は P4 の **同じ** `TrustedSearchScope` と `AuthorizedSourceScope` を入力にする private `VisibleClaimBinding` を返し、pin 後の `selector_for_visible(binding, generation)` で Source・generation・subject/field を再検証する内部拡張とする。別の actor mint / Source visibility decision はない。未知・他 tenant・不可視・失効 ID はすべて同じ `200 DiscoveryEvaluation`、`evidenceSufficiency=unresolved`、`REQUIRED_CLAIM_UNRESOLVED` の非識別的 blocking gap とする。該当 Claim を required 集合から削除せず、selector/value/Source を trace や validation error にしない。catalog 未配線ならこの経路を有効化せず、full Discover を公開しない。

P1 `bodyRequired` は per-request `BodyOnly` と同じ pinned `BodyUnitManifest` / 実検索可能 lexical Unit doc の seal、親 `ResourceVersionRef`、`ContentPartRef`、authoritative representation、`RawBinding`、profile/locator/text digest、現在の `PUBLISHED`・非 T10・`Read` が揃った verified Unit hit だけを肯定結果とする。title、Graph、vector、raw locator は body match にならない。`document.body.contains_exact` の positive は `Completed + Supported` **または**検証済み `Completed + Partial` Unit に限り、Partial の blocking coverage gap と global incompleteness を残す。negative `Absent` は全可視 authoritative item が `Completed + Supported`、有限 scan が全 Unit を調べ、Source-owned `ExactTextNegativeProof` と current binding が一致した場合だけ。Partial/Unsupported/Failed/no-hit/timeout は absent ではなく `unknown` + blocking gap。HTTP が必要な query・Claim selector の expected bytes・親・predicate を同じ正規化済み値に束縛できなければ body claim を作らない。P1 の最小 `KnowledgeUnit` 型・codec の現行コードはこの full-body evidence/coverage をまだ提供しない。

P3 の Graph は一つの `TypedRelationInstance` を一つの typed n-ary relation とし、同一 relation ID の全 participant と metadata を Source/generation/temporal/current access で検査する。Graph path は `PublicTrace`、citation、Primary evidence として公開しない。final gate で一人でも不可視・Unknown・失効ならその relation/path 由来の candidate、evidence、rank、count、trace を一体で除去する。P3 の READY/pin/guard は P7 が接続するまで API の current 読取り保証ではない。

P4 の remote mode は `REMOTE_ENUMERATION`,`REMOTE_QUERY`,`DIRECT_ADDRESS`,`LIVE_ONLY` の四つ。完全 terminal page と同一 snapshot の列挙、または登録済み authoritative direct absence の検証済み receipt だけが `Absent` の候補になる。query no-hit、通常 404/403、`LIVE_ONLY` miss、outage は `Unknown`。一 Source/evaluation につき sealed generation は一つ、同じ verified snapshot/scope にできない追加 action は新 evaluation と typed gap に送る。stable native ID と current access を備えた candidate だけが資格対象で、ID なし ephemeral は `UNSUPPORTED_COVERAGE` gap、GET link/probe/materialization なし。provider の score、role、origin、URL は権限・証拠・fetch 先に使わない。

## 3. P4 と共有する二段階 disclosure lifetime

P4 の **五つ**の retention mode をそのまま採る。`PERSISTENT_RESOURCE` は grant された再生成可能 projection、`PERSISTENT_DISCOVERY_METADATA` は field proof がある metadata のみ、`CACHE_WITH_EXPIRY` は actor/access revision と provider TTL 内の bounded RAM、`SESSION_ONLY` は同じ trusted session の RAM と絶対・idle 期限、`NO_RETENTION` は evaluation RAM と最終開示中だけである。retention が緩んでも古い entry を昇格せず、厳格化・取消・session close・期限で全派生 handle を無効化する。`SessionWorkingSet` の現行参照 API を remote lease と見なさない。

P4 plan §P4-07/13 の将来の `RemoteOwner`/`RemoteLease`、`ScopedDiscoveryService::discover(...) -> Result<TransientDisclosure<DiscoveryResult>, SearchError>`、`CurrentDisclosureAccessPort::authorize(owner, disclosed_fields)`、`TransientDisclosure::with_disclosure(...)` を P5 の同じ application 境界として使う。HTTP handler が裸の `DiscoveryResult`、`Arc`、`Clone`、`Serialize` を取得する port は設けない。Search/GET/SourcePage も同じ owner/gate で safe DTO への借用 view を作る。これらの lease/port は**設計・計画上の interface**であり、現行 `scoped.rs` に実装されたという主張ではない。

`NO_RETENTION` の所有を次の二相に固定する。

1. `EvaluationLease` は provider response、sealed evaluation generation、projection、Graph、probe、receipt、materialization bytes、selector、内部 trace を所有し、evaluation の success/error/cancel/deadline のどの出口でも close して再読不能にする。許可済み返却 field だけを `TransientDisclosure<T>` に移す。
2. `TransientDisclosureLease` は final actor/Source/item/field/Graph participant gate、private safe DTO と bounded serialization/send の間だけ生きる。HTTP body の **socket 送出完了**で close する。handler が response object を返した時点で close して送信中の borrow を壊してはならない。body 生成失敗、write 失敗、disconnect、cancel、timeout、drop の各経路も body owner の finally/drop guard が lease と未送出 buffer を閉じる。gate 前には一 byte も streaming せず、gate 後も有限 deadline/backpressure の下で送る。送信済み bytes を server 側に保持しない。

両 lease の owner/current/revision/retention は read/write と await 後の返却直前に再確認する。`NO_RETENTION` 由来の content、候補 ID、provider cursor/snapshot、query/result trace、digest、具体 gap、body/metadata、per-call provider-derived telemetry を session/cache、公開 cursor、Graph/Projection、audit/log、fixture、temporary spool、background queue、retry buffer、dump に置かない。テストは送出成功・途中失敗・取消・期限後の store と保持済み handle の再読不可を確認する。local Source の許可済み non-retention field であっても同じ二相制約を適用する。

## 4. Cursor、期限、公開予算

初期 cursor は OS CSPRNG で生成する衝突検査付き **128-bit UUID v4 の不透明な RAM handle** とする。handle 自体を bearer secret として URL/access log、trace、analytics から除き、payload を encode/sign して client に渡さない。RAM state は tenant、同じ actor/session/access revision、canonical request digest、可視集合 stamp/digest、認可済み Source の generation/snapshot と最小 continuation、S1 の last key、retention ceiling、期限だけ。raw query、body、snippet、evidence、provider credential、自由文字列 trace は保持しない。`NO_RETENTION` が完全性に必要な Source の provider-derived continuation は RAM cursor/cache にも置けず、Search は `nextCursor=null`、`partial=true`、`PAGINATION_UNAVAILABLE` gap にする。`PlanningOnly` の list slice を page と呼ばない。

Search は全ての必要 Source に安定した continuation とその保持 grant がある場合だけ cursor を発行する。SourcePage は actor-visible catalog の authoritative visibility stamp または canonical visible-set digest と安定 keyset がある場合だけ発行する。次 page で session/actor/tenant/access revision、visibility、generation、request digest/page size、provider snapshot、policy/retention、expiry が変われば理由を分けず `409 CURSOR_STALE`。current access は毎 page に再適用する。session を resolver が束縛できない場合は cursor を発行しない。Discovery は一回の bounded evaluation で cursor を持たない。

P5 案の query 2,048 UTF-8 bytes、purpose 512 bytes、`sourceIds` 16、`requiredClaimIds` 1〜16、page size 既定 20/最大 100、RAM cursor 絶対 5 分/idle 1 分、Discovery actions 16/optional initial Sources 8/evaluated candidates 200/qualified 50/evidence 64/gaps 64/trace 64 は **資格試験の初期候補**であり business SLO でも実配備値でもない。cursor 期限はこの上限、actor/session、provider TTL、Source grant の最短値。HTTP operation deadline は trusted scope と各依存 call、final gate、serialization に伝播させ、別 ref の 30 秒を接続済み設定と見なさない。P1/P4/P7 の PoC と workload で値を固定し、その値と超過時の typed gap/Problem を OpenAPI・config・試験で一致させる。安全な final DTO が期限内に確定しなければ 504、非 timeout の必須基盤障害は 503 とし、途中 buffer を送らない。

## 5. RFC 9457 Problem の wire 決定

P5 の全公開 Problem は `Content-Type: application/problem+json`、`type: "about:blank"` とする。これは [RFC 9457 §4.2.1](https://www.rfc-editor.org/rfc/rfc9457.html#section-4.2.1) の登録済み generic HTTP problem type で、RFC の primary identifier は `type`、この選択での意味は HTTP status の一般 class である。`code` は **P5 Error Registry に定義する extension**として P5 client の詳細な分岐に使う。異なる `code` が同じ `type` と status を共有し得るため、P5 改訂 1 の `type = urn:knowledge-platform:problem:<CODE>` と「type/code 一対一」は撤回する。未登録の `knowledge-platform` URN namespace を RFC 適合 URI として扱わない。公開 documentation host の選定は不要である。[RFC 9457 §3.1.1–3.2](https://www.rfc-editor.org/rfc/rfc9457.html#section-3.1.1) は `type` を primary identifier とし、extension member を許す。

`title` は `about:blank` に従い、その HTTP status の推奨英語 reason phrase に固定する（将来 locale を実装する場合だけ同 status の翻訳）。413/422 は [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5)、429/431 は [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html#section-4) の名称を使う。`detail` は次表の `(status,code)` ごとの固定文のみで、Source、Claim、resource ID、query、SQL、locator、可視性の失敗理由を補間しない。実 HTTP status と body `status` は一致し、`instance` は省略する。`trace_id` は無作為な correlation extension、`retryable` は許可済み公開 retry policy、`errors[]` は 422 等の公開 request field pointer/code のみ。全 error と認可前 parse error に `Cache-Control: private, no-store`、`X-Content-Type-Options: nosniff` を付ける。404 の全隠蔽ケースと 409 の全 cursor failure は body/header/detail が同じである。

| HTTP/body status | `title` | `code` | 固定 `detail` |
| --- | --- | --- | --- |
| 400 | `Bad Request` | `MALFORMED_REQUEST` | `The request could not be parsed.` |
| 401 | `Unauthorized` | `AUTHENTICATION_REQUIRED` | `Authentication is required.` |
| 403 | `Forbidden` | `FORBIDDEN` | `The operation is not permitted.` |
| 404 | `Not Found` | `RESOURCE_NOT_FOUND` | `The resource was not found.` |
| 409 | `Conflict` | `CURSOR_STALE` | `The cursor is unavailable.` |
| 413 | `Content Too Large` | `PAYLOAD_TOO_LARGE` | `The request content is too large.` |
| 415 | `Unsupported Media Type` | `UNSUPPORTED_MEDIA_TYPE` | `The request media type is unsupported.` |
| 422 | `Unprocessable Content` | `VALIDATION_FAILED` | `The request fields are invalid.` |
| 429 | `Too Many Requests` | `RATE_LIMITED` | `The request rate limit was reached.` |
| 431 | `Request Header Fields Too Large` | `REQUEST_HEADERS_TOO_LARGE` | `The request headers are too large.` |
| 503 | `Service Unavailable` | `IDENTITY_UNAVAILABLE` | `A required service is unavailable.` |
| 503 | `Service Unavailable` | `DEPENDENCY_UNAVAILABLE` | `A required service is unavailable.` |
| 504 | `Gateway Timeout` | `TIMEOUT` | `The operation timed out.` |

この表は P5 用の固定 mapping とする。`MALFORMED_REQUEST` は JSON/encoding、422 は公開 field の形式・範囲違反だけ。404 は Resource GET の target 非開示、409 は不明/失効/別 session/不一致 cursor。503 `IDENTITY_UNAVAILABLE` は trusted resolver、`DEPENDENCY_UNAVAILABLE` は可視 snapshot 等の必須基盤であり、隠れた個別 Source の障害を classification に使わない。`Retry-After` と `retryable` は公開 policy が安全に確定する場合だけ付ける。`title`/`detail` は machine 分岐に使わない。HTTP reason phrase の固定文字列は OpenAPI/handler parity で確認する。RFC 9457 の `about:blank` と status/title の規則は [同 §4.2.1](https://www.rfc-editor.org/rfc/rfc9457.html#section-4.2.1) による。

既存 `spec/operations/error-handling-resilience-requirements-v0.md` §7 の URN 例と code 中心の汎用説明、別 ref の `document-api-http/src/error.rs::ApiProblem::new` は P5 と異なる既存契約である。P5 writer は §15 に **P5 Search API に限定した**上記 type/code/status/title/detail/headers の規範と Error Registry を追記し、Document HTTP 全体の URN flow を黙って書き換えない。共通 Problem module に抽出するなら Document 側は別の明示的な contract diff・試験・変更権限を要する。[OAS 3.2.1](https://spec.openapis.org/oas/v3.2.1.html#operation-object) は operation ごとの security と response/schema を定義できるので、四 route で実配線の security scheme、`application/problem+json`、全 status/headers/DTO を一つの契約へ揃える。埋込 Schema Object の既定 OAS dialect と独立 `.schema.json` の `$schema` は区別する。[OAS 3.2.1 Schema Object](https://spec.openapis.org/oas/v3.2.1.html#schema-object)。
