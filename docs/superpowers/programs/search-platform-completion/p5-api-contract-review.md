# P5 Full API — 凍結入力・wire 照合の独立レビュー

- 判定: **NO-GO — Full API Design Freeze**。`p5-api-contract-reconciliation.md` は P5 architecture recheck の二つの主要残件を意味上ほぼ解消したが、下記の source-neutral port と HTTP error wire が未確定。これは P4 全体の実装判定や P5 公開資格の判定ではない。
- 対象: `p5-api-contract-reconciliation.md` SHA-256 `a17920c81928c638ea11204f6dce5e62a0c72d52a286431c70d743dd62d8c12e`。同書が列挙する P5 改訂・再レビュー、P1 minimal/full freeze、P3 freeze、P4 freeze の SHA-256 は現物と一致した。追加で P1 Archive binding ruling `eadaa11a8c02953f48e533c53d549e9b26f346dc862231d3d7622a9ee615599c`、P7 draft、現行 port を read-only 確認した。

## Freeze を止める指摘

1. **[P1] 四 operation 共通の local+remote 可視 catalog に exact port 型がない。** 追補 `:13-18,22,44,109` は P4 `ScopedSourceRegistryPort` を唯一の入口にすると固定し、local Document も同じ `AuthorizedSourceScope` で扱う必要を認める。しかし現在の `ScopedSourceRegistryPort::visible_sources` は `Vec<VisibleSourceRegistration>`、その `registration` は `RemoteSourceRegistration` のみ（`crates/search-application/src/scoped.rs:206-240,277-283`）。実装 `TrustedVisibleRegistry` も `RemoteRegistrationCatalog` だけを列挙する（`crates/search-application/src/remote_registration.rs:649-720`）。`SourceRegistrationLedgerPort::reconcile` も remote-only map を入力にする（同 `:332-349`）。追補が「source-neutral view が必要」と記すだけでは、四 route の complete actor-visible snapshot、local Document の registration/activation/visibility current、SourcePage capability DTO の同一型への写像が一つに定まらない。**修正:** P4 の scope/mint を再利用したまま、local と remote を保持する source-neutral registration view、その `visible_sources` の返却型と current/ledger binding、complete snapshot の失敗条件を契約として定義する。P7 draft の物理 ledger を既存実装と見なさない。追補 `:18,20` の `SourceRegistrationLedgerPort::current` は実 port 名 `is_current`（同 `:344-348`）と揃える。

2. **[P1] 401 の必須 challenge header が Error Registry から抜ける。** 追補 `:81-103` は `401 AUTHENTICATION_REQUIRED` を全公開 route の固定 Problem とし、全 error の `Cache-Control: private, no-store` / `X-Content-Type-Options: nosniff` を要求するが、`WWW-Authenticate` を定義していない。[RFC 9110 §15.5.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.2) は 401 を生成する server に、対象 resource に適用できる challenge を含む `WWW-Authenticate` を必須とする。追補 `:16,103` は実配線前に bearer/cookie/mTLS を捏造しないという正しい境界なので、**修正:** 実 transport の認証方式に適用できる challenge と header を 401/OpenAPI/handler parity の必須条件にする。方式が challenge を提供できないなら 401 mapping 自体を実配線に合わせて再判定する。合成 self-principal だけの HTTP canary はこの条件を満たさない。

3. **[P2] 504 が内部処理の期限切れまで無条件に広がる。** 追補 `:77,99,101` は final gate や serialization に operation deadline を伝播したうえで、安全な DTO を期限内に確定できなければ一律 `504 TIMEOUT` とする。[RFC 9110 §15.6.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6.5) の 504 は gateway/proxy として必要な upstream 応答を待った timeout を表す。local final gate または自己の serialization の期限切れはその条件を満たすとは限らない。**修正:** upstream wait の 504 と内部 deadline failure を分け、後者の適切な status/code/title/detail を registry と OpenAPI に固定する。partial 200 は追補 `:48,77` の安全な独立結果が期限内に確定した場合だけに保つ。

## 整合を確認した境界

- **P1:** `bodyRequired` は per-request `BodyOnly`、実検索可能 Unit doc と manifest の seal、親 Version/Part/raw/current Read に束縛される（追補 `:52`、P1 freeze `:11-13`）。`Completed + Partial` の verified Unit は positive を作れるが blocking gap と global incompleteness を残す。negative は Source-owned finite full scan の `ExactTextNegativeProof` があるときだけで、Partial/no-hit/outage は `unknown`。Archive leaf の binding ruling はこの「verified Unit」の内部検証として継承されるが、追補の exact input 列 `:5` には ruling の SHA がない。次版の入力列に加え、part-wide scalar `archive_inner_format` を要求しないことを明記する。
- **P3:** typed n-ary relation 全 participant と metadata を同じ Source/generation/current access で評価し、不可視 participant があれば relation/path 由来の公開 item/evidence/count/trace を除去する（追補 `:54`、P3 freeze `:9-10`）。Graph path を public citation/Primary にしない。P7 READY/pin/GC の物理接続は別 gate のまま。
- **P4 と retention:** P4 `TrustedSearchScope` / `AuthorizedSourceScope` を再利用し、二つ目の actor/Source mint を作らない（追補 `:10-22`）。`EvaluationLease` は evaluation 終了時、`TransientDisclosureLease` は body の socket 送出完了または error/disconnect/cancel/deadline/drop 時に閉じる（`:60-69`）。gate 前 streaming、NO_RETENTION 由来の cursor/RAM再利用/log/audit/fixture/spool、送出後の handle 再読は禁止。これらは設計上の正しい区別であり、現行の `scoped.rs` に lease が実装済みという意味ではない。
- **公開結果:** Source visibility を routing/lookup より先に確定し、未知・他 tenant・不可視 `sourceIds` と required Claim を識別不能にする。required Claim は欠落させて `sufficient` にせず、opaque `unresolved` + blocking gap にする（`:22-31,48-50`）。P1 body coverage、P4 stable/ephemeral、S1 `PriorityConcat`、typed gap/completeness と source/item/field final gate の方向は凍結入力に整合する。`about:blank` は [RFC 9457 §4.2.1](https://www.rfc-editor.org/rfc/rfc9457.html#section-4.2.1) の generic HTTP problem type として有効で、`type` が主識別子、`code` は追加の分岐用 extension でよい。異なる `code` が同じ `about:blank` を共有するのは誤りではない。413/422 と 429/431 の `title` は [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5) / [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html#section-4) の推奨 reason phrase と一致する。既存 Document HTTP の URN 契約を暗黙変更しない切り分けも適切。
