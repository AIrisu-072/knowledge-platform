### ローカルLLMによる自律検索（2026-10-07）

[処理方式の設計案](../../specs/2026-10-07-search-retrieval-processing-design.md)のL2・L3を試す実験（`experiments/search-validation-corpus/agent`）。Bonsai2 27B（Ternary、vLLM、所有者のGPUマシン）に、語の一致の検索（Search）、意味の検索（Discover、Vectorの下限0.87）、本文の読込み、メモ、回答のツールを渡し、1問60回までツールを使わせた。本文の読込みはコーパスの原文から行い、Document APIの取得経路は通していない。調整用の質問だけを使った（本文lane 39問）。

| 条件 | Recall@10 | Recall@1 | 該当なしの誤検出（4問） | 引用の一字一句一致 | ツール呼出（平均/最大） | 1問の時間p50 |
|---|---|---|---|---|---|---|
| A 最小の指示・簡素なツール説明 | 0.955 | 0.939 | 0.5 | 0.84 | 15.8 / 61 | 167 s |
| B 手順つきの指示・詳しい説明 | 0.886 | 0.886 | 0.25 | 0.85 | 19.7 / 62 | 235 s |
| C Bに使い方の手引き（Skill相当） | 0.900 | 0.886 | 0.25 | 0.90 | 23.8 / 61 | 224 s |

検索の土台だけ（調整用、Discover下限0.87）のRecall@10 0.629に比べ大きく上がった。条件間の差は、自動生成の多段（2語を並べただけの質問）と該当なし4問でほぼ決まり、数が少なく結論は出せない。自動生成の多段は「両方を結ぶ文書」を探して該当なしと答える例が多く、質問の作り方の問題である。代わりに、文書間のリンクをたどる質問を17問作った（`questions/stage1-bridge.jsonl`、アシスタントが本文で確認、人は未確認）。画像対応に切り替えた後のBonsai2で解かせた結果：根拠文書のRecall@10は条件A・Cとも0.735（2文書とも挙げたのは9/17）。回答の正しさはAが14/17、Cが15/17（期待した文字列との照合に手で補正）。Cは引用の一字一句一致が0.92、ツール呼出は平均13.6回で、1問p50は96秒（Aは9.0回、54秒）。誤りのうち2問は質問の書き方があいまいだった（「〜と言った漫画家」を発言者と読んだ、「媒体を開発した企業」を販売元と読んだ）ので、質問を直した。同じ17問をLLM無しで測ると、Search（語の一致）のRecall@10は0.088（自然文の質問がほぼ当たらない）、Discover（Vectorあり、下限0.87）は0.647で2文書とも上位10件は7/17、p50 83 ms。

「該当なし」の質問が少ない（調整用4問）ため、話題は文書群にあるが問われた事実が無い質問を13問追加した（`questions/stage1-noanswer.jsonl`、全文で鍵となる語の組合せが無いことをアシスタントが確認）。質問IDのhashで調整用2問・最終評価用11問に分かれた。エージェントの採点に、期待する答えの文字列を含むかの判定を加えた。1問の文脈は平均8万〜12万トークンで、時間の大半はLLMの処理。

### 画像PDFの読取り（2026-10-07）

GPUマシンのBonsai2は、vLLM向けの非公式変換が画像を読む部分（vision tower）を外したものだった。公式のBonsai2は元のQwen3.8-27Bの画像部分を同梱している。所有者の指示で、同じ画像部分（Qwen3.8-27B NVFP4版に含まれるBF16の重み）を戻し、画像も扱える1つのモデルとして起動し直した。金融庁告示PDFの2ページを画像で読ませた（`scripts/vlm_ocr_probe.py`）。横書きのページは文字の誤り率1.3%。縦書き・90度回転の新旧対照表は31〜77%で、誤読に加えて「改正前」の欄に「改正後」の文を写しており、改正の差分が失われた。このページはPDFの文字層を取り出しても縦書きの順序が崩れる。PDF読取り器は、文字が無いPDF、画像を含むPDF、本文Unitが2つ以上のPDFを扱えない（`crates/search-extraction-worker/src/readers/pdf.rs`）。

[設計](../../specs/2026-10-07-search-generation-segments-design.md)の段1（Unit一覧を文書版×内容部分ごとの不変の部品と一覧で保存、PR #99）を、1,000文書の実環境で変更前と比べた。1回ごとに合成の小さな文書を1件登録・公開し、検索で見つかるまでを測った（`scripts/reflect_probe.py`、5回）。両方ともVectorは止めた（Vectorの保守と更新処理を同時に動かすと、workerがCPUを使い切って更新が20分以上止まったため。段3で扱う）。

段2のうち、古い世代の回収（T7）と、Unit索引を前の世代から作る変更（T8：segmentファイルのハードリンク、変わったUnitだけ削除・追加、復号済みsegmentとファイルdigestのプロセス内キャッシュ）を入れて同じ計測をした。1件の反映は13.7〜28秒（定常状態で14〜15秒）、workerの1件あたりの処理は18.4秒→8.5秒（字句索引の作成 7.5秒→1.3秒、検証と保存 8.5秒→5秒）、workerのメモリは最大4.6 GBで頭打ち。古い世代の回収が効き、字句索引のディスクは2世代・159 MBで一定（回収前は20世代・3.0 GB）。残りの大半は、全Unitに対する検証（本文のSHA-256の再計算、字句の論理digest、seal の照合）と、検索サーバーの読込み（約5〜6秒）。

続けて、確かめた部品の検証を同じプロセスで省く変更（T10a）と、現在の世代に含まれる変更だけのイベントを即座に完了させる変更（T11）を入れた。

### 1万文書（2026-10-07、`MALLOC_ARENA_MAX=2`、Vector停止）

同じダンプから1万記事に増やし（`corpus/jawiki-10k`、293 MB、既存970記事を含む）、worker を止めて新しい9,029文書を登録した（約70秒、イベント27,091件）。手順は `~/kp-validation-data/tenk.sh`（repository の外）。

| 項目 | 結果 |
|---|---|
| 全件の作り直し | 771秒、worker の最大メモリ 10.5 GB（検証環境12 GB） |
| 部品 | 10,207件・472 MB、字句索引 901 MB |
| 最初のイベント（起動から処理まで） | 75秒 |
| 溜まったイベントの処理 | 30分で1,118件（約1.6秒／件）、残り25,972件（このままで約12時間） |
| 処理中の worker のメモリ | 最大 11.1 GB |
| 新しい世代での最初の検索 | 42.7秒（検索サーバーの読込み） |

続けて、配信の待ち時間をなくす変更（処理したサイクルの直後は待たずに次を取る）と、文書のイベントをその文書の記録だけで判定する変更を入れた。溜まったイベントの処理は約0.7件／秒から約25件／秒になり、残り約25,800件は約20分で空になった。その直後の最初の検索は63秒かかり、検索サーバーのメモリは10.8 GBに達し、worker はメモリ不足で停止した（検証環境の空きは71 MB）。

1万文書では、メモリが検証環境の上限に達し、溜まったイベントの処理と検索サーバーの読込みも実用にならない。1件の反映は、イベントが溜まっていたため測れていない。原因は、全 Unit を何度も保持すること（T12）、イベントを1件ずつ処理すること（まとめて完了させる仕組みが無い）、検索サーバーが世代全体を読み直すこと（T10b）。

### 検証コーパスでの組合せの比較（2026-10-15）

JDocQAと同じ再現を、検証コーパスの本文Unit（変換後テキストの空でない行、27万1,875件）で行った（`scripts/corpus_fuse.py`、`corpus_paired.py`）。字句はUnitごとにBM25とゲートを計算し、文書は最良のUnitで並べる。VectorはUnit上位1,024件（実装の8倍の枠）を文書にまとめる。RRFの重みはJDocQAの検証用で選んだ値（EG2 素 w0.6・k1、ruri-v3と合成λ0.5は w0.5・k0）をそのまま使い、検証コーパスでは調整していない。gated_rrf は「ゲートを通った字句の候補を先頭に置き、残りをRRFで埋める」組合せ。

- 再現の確認：ゲートあり字句は最終評価用（自動生成＋LLM、答えのある76問）で Recall@10 0.711・MRR 0.717・該当なしの誤検出 0.538。実装で測った値（0.724・0.743・0.538）と、Recall@10は1問差、誤検出は一致。

|---|---|---|---|
| 字句（ゲートなし） | 0.967 | 0.684 | 0.830 |
| 字句（ゲートあり） | 0.711 | 0.632 | 0.717 |
| Vector | 0.783 | 0.566 | 0.672 |
| 現行の組合せ（ゲートあり字句→Vector） | 0.941 | 0.776 | 0.887 |
| RRF（JDocQAで選んだ重み） | 0.980 | 0.724 | 0.869 |
| gated_rrf | 0.980 | 0.770 | 0.898 |

- RRFだけでは、検証コーパスのRecall@1が現行より下がることがある（合成λ0.5で −12.5pt、符号検定 p=0.019）。短い質問ではゲートを通った候補がほぼ正解で、現行はそれを先頭に置いているため。
- gated_rrf は現行と比べ、検証コーパスで Recall@1 −0.7pt（差なし）・Recall@10 +3.9pt（76問で p=0.06、調整用とbridgeを含む128問で +5.1pt・p=0.002）。JDocQAでは Recall@1 +3.4〜4.8pt・Recall@10 +5.9〜6.7pt・MRR +4.5〜5.5pt（3モデルとも McNemar p<1e-4）。RRFだけと比べると、JDocQAでは1.1〜3.2pt低く、検証コーパスのRecall@1は2〜10.5pt高い（有意なのは合成λ0.5）。両方のデータで、現行より有意に下がった指標はない。
- タイトル：文書側を `title: 文書名 | text: 本文` で埋め込むと（実装は `title: none`）、Vectorだけでは EG2 素の Recall@1 +15.1pt（p=0.019）・MRR +10.8pt（p=0.015）、128問ではどちらも p<0.001。gated_rrf では上乗せは1〜3問分で有意でない。JDocQAにはタイトルがなく、業務文書のタイトルでの効果は未確認。
- 合成λ0.5：素のEG2との差が出るのはタイトルありのVectorだけ（MRR +2.0〜2.6pt、有意）。タイトルなしと gated_rrf では差なし。以前の調整用52問での +4.8pt（Recall@10）はタイトルありの値。
- 提案：Discoverの組合せ（`FusionStrategy::PriorityConcat`、S1方針）を「ゲートあり字句 → 重み付きRRF（ゲートなし字句・Vector、順位のみ）」に替える。該当なしの判定は組合せとは別に、ゲートの有無とVectorの類似度の下限で扱う。タイトルを付けた埋め込みは選択肢（索引の作り直しが要る）。どれも仕様の判断。

### 世代の切替で検索が止まる問題（1万文書、2026-10-10）

- 原因：DBの現在の世代が変わると、ホストは新しい世代の検証と読込み（`DurableDocumentReadModel::load`）が終わるまで、全部の要求を待たせる。負荷なしで1回3.6〜4.8秒。内訳は、射影の読出しとJSON解析0.7〜0.9秒、区画の要約の連結・digest照合0.35〜0.5秒、字句索引の照合0.9〜1.3秒、Graph行0.25〜0.3秒（読込みでもう一度0.19秒）、射影の登録0.4〜0.7秒など。切替中のホストのCPUは最大170%（9 CPU中）で、待ち合わせが長さの原因。
- 対策（検証する内容は変えない。123ceda、202fda1）：検証の中でGraph行を復元・照合と並行して読む。検証で得た所有者を読込みで使い回す。字句索引の照合を「保存済み索引の読出し」（復元と並行）と「突き合わせ」に分ける。検証の間に、射影の登録と字句索引を開く処理を進める（外に出すのは検証が通ってから）。同じ世代の復元は1本にする。

- 追加（64ac5d4）：分割保存された射影の行を、行全体のテキストとチャンクの両方で受け取っていた（1万文書で91 MB余分）。チャンクだけにして、止まりは2.8秒・2.2秒。
