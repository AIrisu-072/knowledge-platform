# 大規模文書・検索精度の検証基盤 — 計画

2026-10-06。基点はmain `8857cb3`（PR #77統合後）、branchは `feat/search-validation-corpus-20261006`。これは検証計画であり、大規模検証を実施済みとは扱わない。結果は[状態記録](status.md)に残す。

## 目的と結論の分け方

実際の文書管理経路で大量の文書を安全に扱えるか（大量文書管理）と、本文から適切な文書・根拠・関係を取得できるか（検索精度）を、別々の指標で確かめる。最終報告は「検索精度」「大量文書管理」「本番運用資格」をそれぞれ別に結論づける。本番運用資格はこの検証では与えない（使い捨ての検証環境だけを使うため）。

## 現在の実装（2026-10-06 確認）

| 段階 | 実装 | 状態 |
|---|---|---|

## 実行環境と資源上限

- 機材：Apple M5（10コア、16 GB）、空き容量43 GiB。Linux専用のsandboxはOrbStack（CPU 10、メモリ8 GB）のLinux machine上で動かす。新しい外部基盤・有料サービスは使わない。
- データの置き場所：`~/kp-validation-data`（repository外）。原文・変換結果・DB・索引・正解の非公開部分はここに置く。repositoryには手順、manifestの雛形、集計結果、匿名化した質問IDだけを置く。
- 上限：検証データの合計20 GiB。空きが15 GiBを切ったら停止。1段階の所要が6時間を超える見込みなら停止して報告。メモリはOrbStackの8 GBを超えない。
- 保持期間：検証終了まで。終了時に削除するか所有者に確認する。

## 検索入力と来歴・正解の分離

- 検索入力：タイトル・見出し・本文。リンクの表示文字と「第○条」「○○法に基づく」等の本文の記述は残す。カテゴリ、既存のrelation、リンク先URL、元ページURL、テンプレート由来のメタ情報は外す。
- ファイル名と文書IDは内容を示さない値（ランダムID）にする。
- 来歴manifest（検索対象外）：出典URL、版・revision、取得日、公布日・施行日、ライセンス、変換履歴、原本と変換後のSHA-256。出典表示に必要な情報は捨てない。
- 正解・質問・採点用manifestは索引にも関係抽出にも渡さない。調整用と最終評価用の質問を分ける。
- Wikipediaの元リンクは関係の正解候補にはできるが、意味的な関係の完全な正解とはみなさない。
- 版・施行日を使う評価は、本文だけの評価と分けて集計する。

## 段階

1,000文書 → 1万文書 → 10万文書。各段階でユニーク文書数・原本ファイル数・版数・抽出チャンク（Unit）数を分けて記録する。複製で件数を増やす負荷試験は、ユニーク文書での精度試験と分ける。小規模で取込みと再現性を確かめてから広げる。

## 実行経路

Document登録API → DB・原本保存 → outbox → `search_outbox_worker`（抽出 → 索引 → 世代公開）→ 検証用Search/Discover API。再取込み、版更新、再起動後の取得を確かめる。メモリ内fixtureだけの成功を全体の成功とは扱わない。検証できた経路とできなかった経路を分けて記録する。

## 評価データ

質問・関連文書ID・根拠箇所（Unit、条項、PDFページ）を対応させる。質問タイプ：同じ語句、言い換え、複数条件・否定・例外、条項の特定、2〜3段階の多段、基準日で有効な規定と旧版の区別、正解が無い質問。人が確認した正解と自動生成の未確認候補を区別し、未確認の正解だけで合格としない。法令は基準日を固定し、改正法と改正後の本文、公布日と施行日を区別する。法的解釈の正しさはこの試験では保証しない。

## 指標

- 検索精度：Recall@k、nDCG@10、MRR、上位10件の取りこぼしを質問タイプ別に。根拠箇所の正確性、関係抽出の誤り、多段検索の成立、該当なしの誤検出。注釈不足で判定できないものは「評価不能」とし「該当なし」と混同しない。ベースラインを測り、失敗を分類してから改善し、同条件で再測定する。目標値を後付けしない。
- 大量文書管理：取込み時間・処理量、失敗・重複・欠落、索引反映の遅延、検索応答のp50/p95/p99、CPU・メモリ・ディスク。一覧のページ送り、原本取得、版更新、公開の切替、予約取消、取下げ、権限変更（実装済みのものだけ）。合成の利用者・閲覧権限で、件数・抜粋・関連文書・直接取得からの漏えいが無いか。再起動・障害・backup/restoreは使い捨て環境だけで。
