## 1. 目的と成功条件

人間がLLM・Agent経由で文書管理システムと検索システムを使った結果から、質問と回答の全文ではなく**傾向**を取り出す。傾向を3種類の改善へ振り分け、ナレッジと検索モデルを継続的に更新する。

1. モデルのファインチューニングとして組み込むもの
2. ナレッジ文書として登録するもの
3. 文書には向かないが、ナレッジとして持つもの

最終目標は、エンジニアではないドメイン知識を持つ業界の利用者が、この改善ループを**自分たちで運用できる**ことである。日常の改善の99%を、エンジニアの作業なしに回せる状態を目指す。運用コストを増やさず、気づきから反映までを短くする。

前提: 単一の企業が社内だけで使う。対象は業務で使う全員。LLMはローカルで動かし、文書・質問・傾向を社外へ出さない。

成功条件:

- 影響の小さい改善は、評価ゲートを通れば承認なしで反映される。影響の大きい改善は、裏で作って評価まで済ませ、改善していれば承認の1操作で反映される。
- 改善の提案は、平易な言葉と根拠（何人が、どんな場面で、どの文書で）を添えて、業界の利用者の画面に届く。承認・却下・取り消しは画面上の1操作で行える。
- どの改善も、反映前に凍結した評価セットで「前より悪くならない」ことを確かめる。確かめられない改善は反映しない。
- 反映したものは世代として残り、1つ前へいつでも戻せる。
- 中身を見せる場面では権限の壁を越えない（11節）。モデルと検索の改善は全部の文書を対象に行うが、検索結果・ナレッジ文書・提案の根拠として見せるときは、見る人の現在の権限で確かめる。
- 質問の全文を既定では保存しない（`spec/operations/observability-audit-requirements-v0.md` 18節）。
- エンジニアの関与は、評価ゲートの連続失敗、基盤障害、仕様の改訂に限る。

今回は設計文書のみを作成する。製品コード、migration、production dependency、HTTP/CLI/GUI、仕様の改訂は作成しない。書面設計の承認後に、別のProduction Implementation Planと、16節の仕様改訂案を作成する。

## 2. 正本と維持する境界

本書は次の現在の契約に従う。`spec/`が規範の正本であり、本書だけで既存の規範を暗黙に変更しない。変更が必要な点は16節に列挙し、別途承認を受ける。

- `spec/architecture/system-architecture-v0.md`（人間・LLM・Agentは同じSearch APIを使う。評価は層ごとに分ける）
- `spec/architecture/architecture-contract-v0.md`
- `spec/data/logical-data-model-v0.md`
- `spec/data/transaction-consistency-requirements-v0.md`（generation、pin、開示前の現在権限の再確認）
- `spec/operations/observability-audit-requirements-v0.md`（2.5節 Evaluation artifacts、18節 Search audit privacy）
- `spec/requirements/frontend-ux-requirements-v0.md`（9節 Risk-based Interaction、20節 Continuous UX Improvement、30節 Trust / Provenance、33節 Progressive Disclosure）

維持する境界:

- Document、DocumentVersion、権限はDocument Platformが正本として持つ。本機能が作るナレッジ文書も、Document APIを通して登録する通常のDocumentである。Searchから直接作らない。
- Searchは再生成可能な投影である。本機能が変える検索の辞書・関係・モデルは、Search Platformの世代として反映する。検索の正本データを別の経路で書き換えない。
- 人間向けとLLM向けで検索の経路を分けない。改善は同じSearch APIの結果として、両方に同時に効く。
- 改善の判断に使う評価セットと評価基準は、人が持つ。ループ自身は評価セットも評価基準も変えない。

## 3. 用語

- **利用シグナル**: 1回の検索・回答から、その要求の処理中だけ取り出す特徴。質問の全文は含めない。要求が終われば、集計に必要な値を除いて捨てる。
- **傾向**: 利用シグナルを一定期間・一定人数以上で集計した結果。個人を特定できない粒度でだけ保存する。
- **改善提案**: 傾向から作る、反映の候補。分類、根拠、影響範囲、評価結果、リスク区分を持つ。
- **ドメイン管理者**: 担当範囲（フォルダ・業務領域）のナレッジに責任を持つ業界の利用者。改善提案を承認する。エンジニアである必要はない。
- **評価セット**: 「この質問ならこの文書が出るべき」という、人が確かめた組の集合。ドメイン管理者が画面で育てる。
- **評価ゲート**: 改善の反映前に評価セットで性能を測り、前の世代より悪くならないことを確かめる関門。
- **ナレッジ変更セット**: 承認された改善をまとめた、世代として反映する単位。

## 4. 対象と保証

### 4.1 対象

- LLM・Agent・人間がSearch APIとDocument APIを使った結果から、利用シグナルを取り出し、傾向に集計する。
- 傾向を、3種類の改善と「対象外」に振り分ける。
- 改善提案を作り、評価ゲートで確かめ、リスク区分に応じて自動反映または承認後に反映する。
- 反映後の効果を測り、悪化を検知したら自動で前の世代へ戻し、ドメイン管理者に知らせる。
- これらを、エンジニアでない利用者が操作する画面で運用する。

### 4.2 保証しないこと

- 改善の仕組みそのもの（評価基準、評価セット、振り分けの規則）を自動で書き換える再帰的な自己改善はしない。部品（辞書、関係、ナレッジ文書、モデル）だけが改善される閉じたループとする。
- 生成用LLM本体のファインチューニングは対象外とする。v0のモデル改善は、検索のEmbeddingとリランカーに限る。
- ナレッジ文書を承認なしで公開しない。
- 質問の全文を学習データや傾向として保存しない。保存するのは、利用者が任意で書いたフィードバックの記述だけとする（6節）。
- 一定人数に満たない行動から、他の利用者に影響する改善を作らない（1人の癖で全員の検索が変わらないための品質の安全策）。
- 回答を作る生成LLM本体の学習は対象外とする。生成モデルは学習した文章を再現し得るため、扱う場合は権限の扱いを別に設計する。

## 5. 全体構成

改善ループは、次の8段で回る。各段は独立して止められ、どこで止まっても検索そのものは動き続ける。

```text
観測 ─ 1回の要求の処理中に利用シグナルを取り出す（全文は保存しない）
  ↓
集計 ─ 一定期間・一定人数以上の傾向だけを残す
  ↓
分類 ─ モデル学習 / ナレッジ文書 / 非文書ナレッジ / 対象外
  ↓
提案 ─ 改善提案を作る（根拠・影響範囲・平易な説明つき）
  ↓
評価 ─ 凍結した評価セットで、前の世代より悪くならないことを確かめる
  ↓
承認 ─ リスク区分に応じて、自動反映 または ドメイン管理者が承認
  ↓
反映 ─ ナレッジ変更セットを新しい世代として切り替える
  ↓
効果測定 ─ 指標を追い、悪化すれば自動で1つ前の世代へ戻す
```

構成要素:

| 要素 | 役割 | 置き場所 |
|---|---|---|
| Usage Signal Extractor | 要求の処理中に利用シグナルを作る。Search APIとAgent連携の境界に置く | Search Platform内（要求の処理中だけ） |
| Trend Store | 集計済みの傾向と、任意のフィードバック記述を保存する。保存期間は無制限 | Search Platform内の別テーブル |
| Improvement Proposer | 傾向を分類し、改善提案を作る。下書きの文章化に手元のLLMを使う | オンプレミスのGPU（外部APIは使わない） |
| Evaluation Gate | 評価セットで改善前後を比べる。検証基盤（search-validation-corpus）を製品に昇格させたもの | Search Platform |
| Knowledge Change Set | 承認された改善を、世代として反映・取り消しできる単位にまとめる | Search Platform / Document Platform |
| 改善の画面 | 提案の受信箱、承認、取り消し、効果の確認、評価セットの育成 | Organization Client |

## 6. 利用シグナル

1回の要求の処理中に、次の値だけを取り出す。質問の全文は取り出した後に捨てる。

| シグナル | 内容 | 保存 |
|---|---|---|
| 結果の利用 | 回答で引用された結果（Resource ID、Version、順位）。上位に出たが使われなかった結果 | 集計して保存 |
| 言い換え | 同じ利用者が短時間に再検索し、後の検索の結果が回答に使われた | 集計して保存 |
| 見つからない | 結果が0件、または回答が「該当なし」になった | 件数と話題のまとまりだけ |
| 明示の評価 | 回答画面の良い・悪いのボタンと、理由の選択肢（古い、見つからない、違う文書など） | 集計して保存 |
| 任意の記述 | 詳しく伝えたい人が自由に書くフィードバック。書くかどうかは任意 | 記述をそのまま保存し、ドメイン管理者だけが読める |
| 未知の語の候補 | 字句検索で一度も出てこない語、同じ文書に行き着く別の言い方 | 18節の承認後、一定人数以上に共通したものだけ |
| 個人の好み | 利用者本人がよく使う文書・言い回し | 本人のMemoryにだけ（他人と集計しない） |

傾向の人数を数えるため、利用者IDは仮名にする。保存期間は無制限とする（所有者判断、16.2節）。人数の下限は初期値3人とし、ドメイン管理者が担当範囲ごとに変えられる。

## 7. 3分類と判定規則

振り分けは、まず決定的な規則で行う。LLMは、規則で決まった提案の文章化と、話題のまとまりの命名にだけ使う。規則で決められない傾向は「対象外」とし、推測で振り分けない。

### 7.1 モデルのファインチューニングとして組み込むもの

- **信号**: 言い換えの後でようやく見つかった文書、上位に出たのに使われなかった文書、話題ごとの「見つからない」。
- **学習データの作り方**: 利用者の質問は使わない。傾向から「どの文書・どの話題で検索が失敗しているか」を特定し、その文書の本文から手元のLLMで学習用の質問を合成する。使われなかった上位の文書を、紛らわしい誤答として組にする。
- **反映**: 定期的に（初期は月次、夜間）Embeddingとリランカーを再学習する。評価ゲートを通ったモデルだけを新しい世代で切り替える。
- **学習データの範囲**: 権限に関係なく、全部の文書から学習用の質問を作る（所有者判断）。Embeddingとリランカーの重みが変えるのは順位だけで、文書の中身を開示しない。開示の可否は、検索結果を返す直前の現在権限の再確認が担う（責務の分離、11節）。

### 7.2 ナレッジ文書として登録するもの

- **信号**: 一定人数以上が同じ趣旨の質問を繰り返し、回答が毎回2つ以上の文書の組み合わせになる、または該当なしになる。
- **作るもの**: FAQ・まとめ文書の下書き。各記述に、根拠の文書と位置を付ける。
- **権限**: 下書きと登録後の文書の閲覧権限は、根拠にした文書すべての権限の共通部分（最も狭い範囲）とする。広げることはドメイン管理者が明示的に行う。
- **反映**: 下書きの作成までを自動で行い、登録と公開はドメイン管理者が承認する。登録はDocument APIの通常の手順（下書き → 公開）を通る。

### 7.3 文書には向かないがナレッジとして持つもの

| 種類 | 信号 | 反映先 |
|---|---|---|
| 略語・同義語・表記ゆれ | 異なる言い方が、同じ文書の引用に行き着く | 検索時の語の展開（辞書） |
| 文書の新旧 | 古い版が引用された後、利用者が新しい版へ移る | 文書どうしの「改訂・廃止」関係（Graph） |
| 一緒に使われる文書 | 同じ回答で繰り返し一緒に引用される | 文書どうしの関連（Graph） |
| 個人の好み | 本人だけの傾向 | 本人のMemory（tenant / service / owner / scopeの境界内） |

辞書は、索引の作り直しを避けるため、検索時の語の展開として持つ。展開を使った検索では、展開した語と辞書の世代を検索計画（Retrieval Plan）の来歴に記録する。展開語を利用者に表示するときは、その語の出どころの文書を見る人が読める場合だけ表示する（社外秘の名称が展開語として見えないようにする）。

### 7.4 対象外

1人だけの傾向、期間内の人数が下限に満たない傾向、機密分類に当たる話題、規則で分類できない傾向は捨てる。捨てた件数だけを指標として残す。

## 8. リスク区分と承認

反映の影響と取り消しやすさで、4段に分ける。区分は改善の種類と影響範囲から決定的に決める。

| 区分 | 例 | 反映 |
|---|---|---|
| R0 | 個人の好み（本人のMemory） | 自動で反映。本人の画面で確認・削除できる |
| R1 | 影響する質問が少ない略語・同義語、文書の関連など、評価ゲートで悪化がないもの | 承認なしで自動反映し、ドメイン管理者に事後に知らせる。1操作で取り消せる |
| R2 | ナレッジ文書、文書の新旧、影響の大きい辞書 | 裏で反映候補の世代を作り、評価まで済ませる。改善していれば、承認の1操作で切り替わる |
| R3 | 検索モデルの切り替え | R2と同じく、再学習・ベクトルの作り直し・評価まで済ませた世代を用意し、評価の報告を添えて承認の1操作で切り替える。エンジニアは評価ゲートの失敗時だけ関与する |

R2・R3では、承認を得てから作業を始めるのではなく、反映候補を先に作って評価し、利用者には「改善した結果」を見せて承認だけを求める。評価で改善が確認できなかった候補は、承認を求めずに理由とともに残す。

## 9. 評価ゲート

- 評価セットは、ドメイン管理者が画面で育てる。検索結果を見て「この質問ならこの文書が出るべき」と記録するだけでよい。
- 評価セットの変更も、承認と世代管理の対象とする。ループが評価セットに書き込むことはない。
- 評価セットの一部を、改善の提案側から見えない保留分にする。提案が評価セットに合わせ込まれていないかを、保留分で確かめる。
- 改善前後を、層ごと（字句、ベクトル、統合、リランク）と全体で比べる。どの指標も、定めた許容幅を超えて悪化しないことを通過条件とする。
- 検索の速さも測る。改善で検索のp95が予算を超える場合は通過させない。
- 通過しなかった提案は、理由を平易な言葉にして画面に残す。同じ種類の提案が続けて通過しない場合だけ、エンジニアに知らせる。

検証基盤（`experiments/search-validation-corpus`）の評価の仕組みを、製品の評価ゲートの土台にする。人手で確かめた正解と自動の正解を分けて扱う既存の原則を引き継ぐ。

## 10. 反映、世代、取り消し

- 改善はナレッジ変更セットにまとめ、Search Platformの反映候補の世代として先に作る。R1は評価ゲートの通過で、R2・R3は承認で、その世代へ切り替える。検索中の要求は、これまでどおり固定（pin）した世代で最後まで処理する。
- 辞書と関係の変更は、索引の作り直しを伴わない。モデルの切り替えはベクトルの作り直しを伴うため、GPUでの一括生成の経路を前提とする。
- ナレッジ文書は、Document Platformの通常のVersionとして残る。取り消しは文書の公開終了で行う。
- 反映後、指標が定めた幅を超えて悪化した場合は、自動で1つ前の世代へ戻し、ドメイン管理者に理由を知らせる。

## 11. 権限と機密（責務の分離）

改善と開示の責務を分ける。

- **改善の責務**: モデル、辞書、関係の改善は、権限の範囲に関係なく全部の文書と全員の傾向を使って総合的に行う。これらが変えるのは順位と候補の集め方であり、文書の中身を開示しない。
- **開示の責務**: 中身を見せるかどうかは、見せる直前に見る人の現在の権限で決める。検索結果の開示前に現在の権限を確かめ直す既存の仕組み（`transaction-consistency-requirements-v0.md`）は、改善の後もそのまま働く。改善で順位が変わっても、見えない文書が見えるようにはならない。

開示に当たるため、権限を確かめる場面:

1. 自動で作るナレッジ文書の本文。閲覧範囲は、根拠にした文書すべての閲覧範囲の共通部分（最も狭い範囲）とし、広げるのはドメイン管理者が明示的に行う。
2. 改善の提案の画面に出す根拠（文書名、位置、例）。見る人が読める根拠だけを表示する。
3. 検索時の語の展開の表示（7.3節）。

その他:

- 個人の好みは本人のMemoryにだけ置き、他人と集計しない。
- 任意のフィードバック記述は、ドメイン管理者だけが読める。
- 文書・質問・傾向を社外へ送らない。提案の文章化と学習は、ローカルLLMとオンプレミスのGPUで行う。

## 12. 業界の利用者向けの画面

エンジニアの言葉を使わず、業界の言葉と具体例で示す。`spec/requirements/frontend-ux-requirements-v0.md` に従う。

- **改善の受信箱**: 提案を1件ずつ、平易な説明と根拠付きで示す。根拠は、何人が、どの期間に、どの文書で困ったかと、評価の質問で検索結果がどう変わるかの前後比較。承認・却下・保留を1操作で行える。
- **反映済みの一覧**: 自動で反映されたもの（R0・R1）も含めて並べる。どれも1操作で取り消せる。
- **効果の確認**: 「見つからない」の割合、言い換えの割合、回答に文書が引用された割合、答えにたどり着くまでの検索回数を、期間で比べる。
- **評価セットの育成**: 検索結果の画面から「これが正解」と記録する。記録した質問は、以後の改善の評価に使われる。
- **週次のまとめ**: 改善の件数、効果、承認待ちの件数を、担当範囲ごとに届ける。

リスクの高い操作（R2・R3の承認、取り消し）は、影響範囲を先に示してから確定する（Risk-based Interaction）。提案と反映の根拠は、元の文書と位置へたどれる形で示す（Trust / Provenance）。詳細は必要な人だけが開く（Progressive Disclosure）。

## 13. 運用コストと速さ

| 処理 | 頻度・目標 |
|---|---|
| 利用シグナルの取り出し | 要求ごと。検索の応答時間をほぼ増やさない（予算は実装計画で定める） |
| 傾向の集計と提案の作成 | 日次。夜間にオンプレミスのGPUで行う |
| R0・R1の反映 | 評価ゲート通過後、1時間以内 |
| R2の反映 | 反映候補の世代を先に作るため、承認の直後 |
| モデルの再学習（R3） | 初期は月次、夜間。再学習・評価まで済ませ、承認の直後に切り替えられる状態で待つ |

- 外部のAPIを使わないため、従量の費用はかからない。計算はRTX 5090等の既存のGPUで、検索の負荷が低い時間に行う。
- エンジニアへの通知は、評価ゲートの連続失敗、基盤の障害、保存期間・権限など仕様の判断に限る。

## 14. 失敗の意味

| 状況 | 振る舞い |
|---|---|
| 利用シグナルの取り出しに失敗 | 検索はそのまま返す。シグナルは捨て、失敗件数だけを残す |
| 集計・提案の作成に失敗 | その日の提案を作らない。検索とナレッジは前の状態のまま |
| 評価ゲートで悪化 | 反映しない。理由を画面に残す |
| 評価ゲートを実行できない | 反映しない。「確かめられなかった」として扱い、通過扱いにしない |
| 反映後の悪化 | 自動で1つ前の世代へ戻し、知らせる |
| 権限の判定が不明 | その派生物を作らない、または最も狭い範囲で作る |

## 15. 段階導入

| 段階 | 内容 | 主な成果 |
|---|---|---|
| 1 | 利用シグナルと傾向の集計、良い・悪いのボタンと任意の記述、効果の確認画面、評価セットの育成画面、略語・同義語の自動反映（R1）と取り消し | 改善の効果を測れる状態と、最初の自動改善 |
| 2 | ナレッジ文書の下書き、文書の新旧・関連、反映候補の世代と承認の1操作での切り替え | 繰り返される質問への文書での回答 |
| 3 | モデルの定期再学習、評価の報告、承認の1操作での切り替え | 検索モデルの継続改善 |
| 4 | R1の範囲を、効果と事故の実績に応じて広げる | 承認の手間の削減 |

段階1はリスクが低く、効果を測りやすい。以後の段階は、前の段階の効果と事故の有無を見て進める。

### 16.2 所有者の判断（2026-10-14）

決定済み:

1. 利用形態: 単一の企業が社内だけで使う。対象は業務で使う全員。LLMはローカルで動かし、社外へ出さない。
2. 保存期間: 無制限。
3. 影響の小さい改善（R1）: 承認なしで自動反映する。
4. 影響の大きい改善（R2・R3）: 反映候補を先に作って評価し、改善していれば承認の1操作で反映する。
5. 学習の範囲: 権限に関係なく全部の文書を使う。改善と開示は責務が違い、開示の可否は開示の直前に確かめる（11節）。
6. 回答の画面に良い・悪いのボタンを置く。詳しく書きたい人のための任意の記述欄を用意する。

未決:

1. 人数の下限の初期値（本書は3人を提案。ドメイン管理者が担当範囲ごとに変えられる）。
2. ドメイン管理者を、誰が、どの範囲に割り当てるか。

## 17. 評価と受入

- 改善のループを1周回し、提案 → 評価 → 承認 → 反映 → 効果測定 → 取り消しまでを、エンジニアの操作なしに業界の利用者が行える。
- 質問の全文が、Trend Store、監査、Telemetry、学習データのどこにも残らないことを試験で確かめる（任意のフィードバック記述は除く）。
- 閲覧範囲の異なる利用者を混ぜた試験で、検索結果・ナレッジ文書・提案の根拠・展開語の表示から、見えないはずの情報が出ないことを確かめる。
- R1が承認なしで反映され、R2・R3が承認の1操作で、評価済みの世代へ切り替わることを確かめる。
- 人数の下限に満たない傾向から、提案が作られないことを確かめる。
- 評価ゲートで悪化した提案、評価できなかった提案が反映されないことを確かめる。
- 反映後の悪化で、自動で1つ前の世代へ戻ることを確かめる。
- 段階1の効果を、「見つからない」の割合と言い換えの割合の変化で示す。
