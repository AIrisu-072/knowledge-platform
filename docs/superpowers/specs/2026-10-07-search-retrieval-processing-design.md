# 検索の処理方式 — 設計案（LLMに左右される部分と左右されない部分の分離）

2026-10-07。状態：**層の分け方は所有者が了承（2026-10-07）。境界の計測と詳細は検討中**。前提と判断材料は[検証基盤の状態記録](../programs/search-validation-corpus/status.md)。

## 1. 前提（所有者の判断、2026-10-07）

- 利用者は人間とAIエージェントの両方。人間はキーワードでも日本語の自然文でも探せる。
- 入力はすべてLLMを通す。人間：人間 → LLM → 検索システム。AIエージェント：LLM → 検索システム。
- LLMを通さない経路は最終手段だけ：LLMにつながらないときのフォールバックと、利用者がGUIで明示的にLLMを使わないと選んだとき。
- LLMはローカル実行のQwen系（現在はQwen3.8 27BベースのBonsai2 27B。Qwen4が1〜2か月以内に出る見込みで、頻繁に入れ替わる）。
- LLMを入れ替えたとき、作業がLLMに左右される部分のベンチマークと修正だけで済むこと。

## 2. 1,000文書の検証で分かったこと（判断材料）

- 字句検索（bigram、語の一致）は語句一致・タイトル・条項・多段に強く、言い換えに弱い（Recall@10：語句一致1.0、言い換え0.533）。
- Vector（E5-small）は言い換え・例外・複数条件に強く、語句一致に弱い（言い換え0.933、語句一致0.412）。
- どちらも「答えが無い」を見分けられない（該当なしの誤検出0.46〜0.54）。類似度や一致率の閾値では、再現率と誤検出の両立ができなかった。
- 本文から文書間の関係を抽出する処理が無く、Graphは文書の配置などの構造しか持たない。多段の質問は字句検索の偶然の一致に頼っている。
- 施行日などの版の情報は検索側に渡っておらず、基準日の質問は評価できない。

## 3. 層の分け方

| 層 | 役割 | LLM | 入れ替え時の作業 |
|---|---|---|---|
| L0 検索コア | 索引（字句・Vector・Graph・構造化情報）、取得、権限確認、根拠Unitの特定、出典、決定的な並べ方 | 使わない | 不要 |
| L1 検索計画の契約 | 検索の要求を表す版付きのJSON（下記）。L0が検証して実行する | 使わない | 不要 |
| L2 LLMアダプター | L2a：質問 → 検索計画（生成型LLM）。L2b：検索結果 → 判定（答えの有無、並べ替え、次の手。判定専用モデルも候補） | 使う（モデルごとのプロンプトと解析） | 差し替えたモデルの側のベンチマークと修正 |
| L3 実行器 | 計画を手順どおりに実行し、予算内で繰り返す。L2を決まった時点で呼ぶ。経過を記録する | 使わない | 不要 |
| L4 規則による計画器 | LLMが無いときの固定の計画（フォールバック） | 使わない | 不要 |

LLMに左右されるのはL2だけ。L0・L1・L3・L4はLLMを知らない。

### L1 検索計画（案）

```json
{
  "planVersion": 1,
  "intent": "lookup | paraphrase | conditions | multi_hop | as_of | browse",
  "keywords": ["名詞や固有名詞", "..."],
  "expansions": ["表記揺れ・言い換え", "..."],
  "semanticQuery": "意味検索に使う短い文",
  "filters": {"asOf": "2026-07-30", "documentTypes": ["..."]},
  "steps": [
    {"op": "lexical", "terms": "keywords+expansions", "scope": "title|body"},
    {"op": "vector", "query": "semanticQuery"},
    {"op": "locateEvidence", "from": "previous", "limit": 10},
    {"op": "expandRelations", "from": "top", "relationTypes": ["参照", "根拠"], "hops": 1}
  ],
  "budget": {"maxSteps": 6, "maxResults": 20}
}
```

- 計画はL1のJSON Schemaで検証する。L2の出力が壊れていればL4の固定計画に落とす（LLMの失敗で検索が止まらない）。
- 権限・テナント・Sourceはサーバーが付け、計画では指定できない（既存のSearch/Discoverと同じ）。

### L2 LLMアダプター

- モデルごとにプロンプト、出力の解析、温度などの設定をまとめる。モデルID・量子化・プロンプト版を記録する。
- 呼ぶ時点は固定する：(1) 計画の作成、(2) 結果の判定（答えの有無、根拠Unitを読んだ上での並べ替え、続けるなら次の手）。
- 文書の本文は「データ」として渡し、命令として扱わない（文書中の指示文によるプロンプト注入の対策）。出力は構造化JSONだけを受け付ける。
- LLMが見るのは、L0が権限確認を通した抜粋だけ。ローカルLLMなので文書は外部に出ない。

### L2b 判定専用モデル（候補：Cloudflare Clef / Clef-flash）

- Clefは文章を生成せず、与えた状況と型付きの問い（はい/いいえ、選択、点数）に、選択肢ごとの確率を1回の計算で返す「判定モデル」（2026-10-01公開、Apache 2.0、重み公開）。Clefは凍結したQwen3.8-27Bに判定用の部品を足したもの、Clef-flashはQwen3.5-9Bがベース。1要求で最大64問。性能値はCloudflareの自己申告で、第三者の再現は未確認。
- 知識の出どころにはしない。根拠はL0の検索結果だけで、Clefには「規則（問いと選択肢）＋検索で取った抜粋」を渡して選ばせる。検索の候補集めにClefの知識を使わないので循環しない。
- 使いどころ（すべて選択肢が列挙できるもの）：質問の種類の判定（`intent`）、候補ごとの「この抜粋は質問に答えているか」と点数（答えの有無・並べ替え）、L1の`op`から次の手を選ぶ。
- 生成型LLM（L2a、Bonsai2など）とは別の部品として扱い、別のベンチマークで測る。生成型LLMを入れ替えてもClefは替えなくてよい。
- 注意：第三者の評価では、この種のモデルは「未知の選択肢からの選択」と検索結果の関連性の判定が強くなかった（arXiv:2610.02267、Clef自体は対象外）。Clef-flashは「どれにも当たらない」の判定が弱い（CLINC150+OOSで66.77、Clefは97.43）。どちらも自前の評価セットで確かめてから採用する。
- 資源：第三者の推定では64k文脈・同時1件でVRAM 85 GB（Clef）／41 GB（Clef-flash）。Workers AIの利用は文書を外部へ送ることになり、ローカル実行の前提と合わない。

### L3 実行器

- 計画の`steps`を順に実行し、前の段の結果を次の段に渡す（候補 → 文書内の根拠 → 関係で展開）。
- L2の判定で「答えなし」「十分」「追加の手が要る」を受け、予算内で繰り返す。
- 経過（計画、各段の件数、判定）を記録し、評価と監査に使う。

### L4 規則による計画器（フォールバック）

- LLMにつながらない、またはGUIでLLMを使わないと選ばれたときだけ使う。
- 固定の計画：字句（bigram、語の一致）とVectorの両方で候補を取り、決定的に統合する。判定は閾値による。精度は今回の計測値（Search Recall@10 0.72）程度を想定する。

## 4. 既存の部品との対応

- L0は既存のSearch Platform（`search-tantivy`、`search-runtime`の永続世代、`vector_store`、`search-graph`、権限確認）。L1の`steps`は既存の`RetrievalInputs`（lexical / vector / graph plan / structured filters / temporal）と`DiscoveryRequest`に写せる。
- 不足しているもの：本文からの関係抽出（`expandRelations`の中身）、版・施行日を構造化情報として索引に持つこと（`asOf`）、Unit単位の根拠特定APIの公開（現在は抜粋だけ）、統合の方式（現在は優先順の連結だけ）。
- 既存のDiscoverのClaim・根拠の十分性の判定は、L2の判定とは別の、決定的な検証として残す（LLMの判断を根拠の代わりにしない）。

## 5. 評価を二層に分ける

| ベンチマーク | 対象 | LLM | いつ回すか |
|---|---|---|---|
| B1 コア | 固定の計画（L4と、質問ごとに人手で用意した計画）でのL0+L3の精度 | 使わない | 検索コアを変えたとき |
| B2 LLM込み | 質問 → L2計画 → L3/L0 → L2判定の、最終的な正しさ（正解文書・根拠・答えなしの判定） | 使う | LLMやプロンプトを替えたとき |

- LLMを替えたときはB2だけを回し、L2を直す。B1の結果は変わらない。
- B2では「計画の妥当さ」（意図の判定、キーワード抽出）も別に採点し、どこで失敗したかを分ける。
- 評価セットは今回のもの（自動生成とLLM作成、アシスタントが本文で確認）を土台にし、人の確認は別に記録する。

## 6. 決めること

1. この層の分け方と、L1を版付きの契約にすることでよいか。
2. 判定（答えの有無）をL2に任せ、L0は閾値で無理に「答えなし」を決めない方針でよいか。
3. 不足部品（関係抽出、版・施行日の構造化、根拠Unitの公開、統合方式）の優先順位。
4. Bonsai2 27Bを動かす環境（この検証環境のメモリ12 GBでは載らない見込み。推論用の環境の確保）。
