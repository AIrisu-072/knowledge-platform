# 検索世代の持ち方 — 不変の部品と一覧への変更（設計案）

2026-10-07。状態：**所有者承認（2026-10-07、§5の判断1〜3すべて合意）**。[実装計画](../plans/2026-10-07-search-generation-segments.md)。根拠の計測は検証基盤の状態記録（PR #86、`docs/superpowers/programs/search-validation-corpus/status.md`）。

## 1. 何が問題か（1,000文書・271,330 Unitでの計測）

今の世代（P7 bundle）は、1件の変更でも、Source全体の完全な写しとして作り直している。

| 部品 | 今の作り方 | 1,000文書での量 |
|---|---|---|
| Unit一覧（本文・位置・来歴） | `search_generation_payload` に1つのJSON（64 MiBずつ分割、migration 0010） | 372 MB、7分割 |
| 字句索引 | 世代ごとのTantivyのディレクトリを全Unitから作り直す（`build_generation_at`） | 291 MB（bigram）、全件68秒 |
| Graph | 世代ごとに全レコードを作る | — |
| Vector | 埋め込みは保存済みの値を再利用する（`values_by_cache_key`）が、世代ごとの stage に全Unitのベクトルを書き直す | 約420 MB（384次元×271,330） |
| 読込み（`durable_read`） | 新しい世代を初めて使うとき、Unit一覧・Graph・字句索引・Vector対応表を全部メモリに戻す | 約10秒、workerは常時4〜5 GB |

1件の更新の反映に7〜8秒かかり、ほぼすべてが写しの作り直しと読み直しに費やされている。量は文書数に比例するので、10万文書では1世代が約37 GBのJSONと約30 GBの字句索引になり、成り立たない。

## 2. 方針

**世代＝変更されない部品の集まりを指す一覧（manifest）**に変える。変わった文書の部品だけを新しく作り、変わらない部品は前の世代と共有する。

```text
文書の変更
  ↓
その文書版のUnitだけ抽出（済：変わらない項目は再利用、8a2cdcc）
  ↓
Unit部品（新）   字句の部品（新）   Graphの差分   Vectorの差分
  ↓
世代の一覧 = [部品の参照…] + 各部品の digest と件数 + 全体の合成 digest
```

仕様は、影響する範囲だけの作り直しを「全件の作り直しと論理的に同じ結果になる」ことを条件に認めている（transaction-consistency-requirements-v0 §1063, §1093）。この案はその条件の中で、保存と読込みの物理的な形を変えるものである。

## 3. 部品の単位と保存

### 3.1 Unit部品

- 単位：1つの文書版（`ResourceVersionRef`）× 1つの内容部分（`ContentPartRef`）× 抽出の版（profile、parser build）。今の `BodyItemEntry` 1件に当たる。
- 内容で決まる digest を鍵にした、変更されない行として保存する（新しい表 `search_unit_segment`、主キーは digest）。中身は今の `BodyItemEntry` と同じ形の JSON。
- 世代の一覧は、Unit部品の digest、件数、順序を持つ（新しい表 `search_generation_segment`、世代×順序→部品）。
- 今の `unit_manifest` の論理 digest は、部品の digest を決まった順序で畳み込んだ値として、一覧から計算し直せる形にする。

### 3.2 字句索引

- Tantivyの索引は、もともと変更されないsegmentファイルの集まりで、`meta.json` が一覧になっている。
- 新しい世代のディレクトリは、変わらないsegmentのファイルを前の世代からハードリンクし、変わった文書だけの新しいsegmentを足して作る。消した文書は削除の印（delete bitset）で表す。segmentが増えすぎたら、背景で統合（merge）した世代を作る。
- 封印（seal）の digest は、ファイルごとの digest の一覧から作る。ハードリンクしたファイルは、前の世代で確かめた digest を引き継ぐ。読み直して照合するのは新しいファイルだけにする（§5の判断1）。

### 3.3 Graph

- 文書ごとのレコード群を部品にし、世代の一覧はその参照と、文書をまたぐ関係の差分を持つ。
- Graphの保存先はPostgreSQLの暫定採用のままとし（2026-10-05の判断）、この案では部品化までにとどめる。

### 3.4 Vector

- ベクトルの値は、埋め込みの再利用の鍵（`EmbeddingCacheKey`）ごとに1回だけ保存する（今もこの鍵で再利用はしている）。
- 世代の stage は値を書き直さず、Unit部品と同じ単位の参照の一覧にする。
- 今も Vector の構築は別のループ（`VectorMaintainer::ensure_current`）で動き、字句の世代の公開を止めない。ただし構築は「その時点の最新の世代」に対して行い、公開は最新の世代が変わっていないことを条件にする（CAS）。更新が続くと、構築が終わる前に世代が進んで公開できず、Vector が古いまま追いつかない恐れがある。参照化で1世代の構築を変わった文書の分だけにし、この遅れを解消する。

## 4. 読込み

- 新しい世代では、一覧と、変わった部品だけを読む。変わらない部品は、前の世代のメモリ上の表現を共有する（部品の digest ごとのキャッシュ）。
- 全部を常にメモリに置かない。本文の抜粋や位置が必要なUnitは、部品を必要になった時点で読む。キャッシュの上限を設定で決める。
- 字句索引はハードリンクしたファイルを開くので、OSのページキャッシュが共有される。

## 5. 所有者の判断（2026-10-07、すべて合意）

1. **確認のしかた**：今は、READY・切替・pin のたびに、保存した値から digest を全部計算し直す（「保存された digest だけを信じない」）。部品化した後もこれを全部の部品で行うと、計算量が文書数に比例したまま残る。提案は次のとおり。
   - 部品は書いたときに一度だけ確かめ、確かめた記録（receipt）を部品に付ける。
   - 世代の切替では、一覧と新しい部品だけを計算し直す。
   - 既にある部品は、プロセスが初めて読むときに確かめる（遅延検証）。

   → 合意。仕様 SD-T11 5 に反映した。
2. **部品の単位**：文書版×内容部分（提案）か、複数の文書をまとめた塊か。前者は変更に強く、後者は件数が減る。10万文書ではUnit部品が約10万件になり、PostgreSQLの行数として問題ない見込み。→ 文書版×内容部分で合意。
3. **背景の統合（compaction）**：字句索引のsegmentが増えすぎたときの統合の条件（segment数の上限など）。→ 実装中に計測してから案を出す。

## 6. 実装の順番と、事前に決める合格条件

1. Unit部品と世代の一覧（3.1）、読込みの差分化（4）。
2. 字句索引の差分化（3.2）。
3. Vectorの参照化（3.4）。
4. Graphの部品化（3.3）。

各段で、全件の作り直しと論理的に同じ結果になることを、同じ入力から両方を作って比べる試験で確かめる（仕様 §1063）。

1万文書の段階の合格条件を、計測の前に次のとおり決める。数値は案です。

| 項目 | 条件 |
|---|---|
| 1件の更新の反映（イベントから公開まで） | p95 10秒以内（1,000文書の今の値は7〜8秒） |
| 新しい世代の最初の検索 | 2秒以内 |
| workerのメモリ | 2 GB以内（今は1,000文書で4〜5 GB） |
| 1世代を増やすときのDB・ディスクの増分 | 変わった文書の量に比例し、全体量に比例しない |
| 全件の作り直しとの論理的な同一性 | digestが一致 |

## 7. やらないこと

- Graphの保存先の変更（P2のまま）。
- 字句の解析方式（bigram）の変更。
- 公開APIや権限の確認の変更。
