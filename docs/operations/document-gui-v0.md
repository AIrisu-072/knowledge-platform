## 文書の属性で一覧を絞り込む

この機能はPR80統合main `1fe1b011` を基点に[PR81](https://github.com/AIrisu-072/knowledge-platform/pull/81)で統合し、初回統合後main `0801c986` に含まれる。PR公開head `426db3a5a43083a1b4bd76b656ea58322019eed3` と、統合後main自身の[push CI](https://github.com/AIrisu-072/knowledge-platform/actions/runs/37407454204)は別実行で、いずれも属性の実GET・詳細往復・HTTP再起動・cleanup・公開artifact0を確認した。現在pinの資格は[手動導入手順](linux-manual-installation.md)の新head欄を正本とし、[属性絞り込みの記録](../superpowers/execution/document-metadata-filters-status.md)の未hosted記述は実装時点の履歴として保持する。旧固定版3d8deb2には含まれない。

1. 「文書」または「編集作業」の一覧を開く。「文書種別」「所管部署」「カテゴリ」に必要な条件を入力する
2. 「絞り込む」を押す。文書名の条件と併用でき、指定した条件がすべて一致する文書を現在読める範囲から表示する。入力している途中では条件を適用しない
3. 属性は部分一致ではなく完全一致で、前後の空白・大文字小文字もそのまま扱う。空欄だけが未指定で、空白だけの入力は空白の値を指定する。Unicodeの表現を自動変換しない
4. 各属性は1024 UTF-8 bytes以下で入力し、制御文字は含めない。不正値は入力を残して理由を表示する。画面の条件を直してからもう一度「絞り込む」を押す
5. 3属性だけを外すときは「属性の絞り込みを解除」を押す。文書名・フォルダー・一覧の種類・並び順・ページ件数は保持する。属性の適用・解除後は最初のページから読み直す

次のページや詳細との往復、ブラウザーの戻る・進むでも適用した条件を保持する。条件はURLにも含まれるため、共有先に見せたくない属性値を含むURLは共有しない。文書の属性を編集する操作ではなく、元の属性・版・権限・既読状態を変更しない。0件と読取失敗は別の状態なので、エラー時は表示された理由を確認する。

属性の空値や欠損だけを選ぶ専用条件、属性候補の一覧、日時条件、未読だけの条件は今回の画面追加に含めない。短い合成値による実GETとHTTPサーバー再起動後の確認、長さ・特殊文字・遅延応答などの純粋/DOM確認は別の資格として記録する。見た目全体の画像比較は未取得のままである。

## 文書の作成日時で一覧を絞り込む

この機能はPR83統合main `dc04ba4a` を基点にPR84で統合した。旧固定導入版 `0801c986` には含まれず、現在pinには含まれる。[作成日時条件の状況](../superpowers/execution/document-created-range-status.md)の初回受入履歴と、[手動導入手順](linux-manual-installation.md)の公開製品headの資格を区別する。

1. 「文書」「編集作業」または履歴一覧で「作成日時の開始（含む）」「作成日時の終了（含まない）」にカレンダーと時刻で入力する。入力はJST / UTC+09:00の分単位で、片側だけでも指定できる。対象は文書自体（Document）の作成日時で、公開日時や版の作成日時ではない
2. 「絞り込む」を押す。入力しただけでは適用しない。開始以上（`createdAt >= createdFrom`）、終了未満（`createdAt < createdBefore`）の文書を現在読める範囲から表示し、文書名・属性・フォルダー、公開一覧の未読条件とも併用できる。適用後は最初のページから表示する
3. 秒・小数秒・別のUTC offsetなど、分単位の入力へ正確に戻せないURLの条件は、適用中の原文を読取り専用で表示する。他条件の適用・ページ送り・並替・詳細との往復でも原文を保持する。日時を変えるときは「作成日時の開始を指定し直す」または終了側の同じボタンを押し、カレンダーと時刻で指定して「絞り込む」を押す。指定し直し中の空欄は解除にならず、理由を表示して適用を止める。「作成日時の開始の指定し直しを取消」または終了側の同じボタンで、その端の元の条件へ戻せる
4. 片側だけ外すときは「作成日時の開始を解除」または「作成日時の終了を解除」を押し、「絞り込む」で適用する。両側をすぐ外すときは「日時の条件を解除」を押す。日時の適用・解除は他の有効な条件と未読条件を保持し、最初のページに戻る。「属性の絞り込みを解除」は日時条件を保持する。解除後は既存の読取cacheを使う場合がある
5. 日時の構文や開始・終了の順序は既存APIが検査する。開始と終了が同じ、または開始が終了より後の場合などの422は、0件の「文書がありません」とは別の読取エラーである。URLと入力を保持するので、表示された理由を確認して日時を指定し直すか解除する。URLの型・転送上限などで取得が止まった場合も、画面の案内から不正な条件を明示解除する

条件はURLにも含まれるため、共有先に見せたくない条件のURLは共有しない。絞り込みは元の文書・属性・版・原本・既読状態を変更しない。既存metadata受入の2ケースへ通常カレンダー入力のGET、精密原文の開始包含・終了除外、詳細往復・HTTPサーバー再起動後の確認を追加している。現在pinの実hosted結果は[手動導入手順](linux-manual-installation.md)の資格記録を参照する。画像比較、全status/headers喪失、対象PC導入・backup/restore・PostgreSQLプロセス再起動・本番認証の資格も追加しない。

## System Root直下にフォルダーを作る

この機能は旧固定版3d8deb2には含まれず、現在pinには含まれる。初回は[PR76](https://github.com/AIrisu-072/knowledge-platform/pull/76)をmain `ce8ed4f15dd564235c4f68a406eec42fd8ca91d4`へ統合した。main自身の[CIと実操作受入](https://github.com/AIrisu-072/knowledge-platform/actions/runs/37334503863)は成功した。[Root作成の記録](../superpowers/execution/document-root-folder-create-status.md)は実装時点の履歴として保持し、旧固定導入版にこの機能があるとは扱わない。

1. 「文書」または「編集作業」の一覧を開き、フォルダー欄の「System Rootにフォルダーを作成」を押す。保存済みの作成要求や確認結果がない新規作成では、別のフォルダーを選択していてもSystem Rootの直下に作成する。要求や確認結果が残っている場合は、どちらの入口でも元の作成先名・IDを表示するので、「登録先」を確認する
2. 「フォルダー名」と「作成理由」を入力する。空欄、名前の改行・制御文字・区切り記号などは使えない。入力例は合成データに限る
3. 「作成する」を押す。送信前にSystem Rootの最新状態を取得し、サーバー側の現在権限・競合・名前重複を確認する。現在実行できない場合は画面の理由を確認する
4. 「フォルダーを作成しました。」を確認し、「確認して閉じる」を押す。成功後はフォルダー一覧を再取得する。一覧の読取りに失敗しても作成をやり直さない

結果が不明なら同じ入口を開き、「同じ内容で再試行」を使う。操作ID・新しいフォルダーID・名前・理由・基準revisionを保持し、新しい作成へ切り替えない。同じアプリ内の画面往復では要求を保持するが、ページ再読み込みやタブ終了で失われる。解決前は離脱を避け、解決しない場合は操作IDを添えて管理者へ結果を確認する。後続の権限エラーや見つからないという応答だけでは、最初の作成が未実行だったとは判断できない。

最初の送信が明確に拒否された場合だけ「最新の状態を取得して見直す」を使う。競合には同名フォルダーの存在も含むため、再取得だけで解決すると考えず名前と状態を確認する。保存前のキャンセルは作成しない。成功を単に「閉じる」で閉じた場合は確認結果が残り、再表示して確認できる。

ce8ed4fに統合した機能はSystem Root直下の作成だけである。非root配下の作成は後続の「選択したフォルダー内に子フォルダーを作る」、続き表示は次節を参照する。改名・移動・ACL変更・既読操作は含まない。ce8ed4f時点の一覧は先頭200件までである。照合済みの成功通知とIDを控え、一覧に見えないことを理由に重複作成しない。画像比較の資格は未取得で、goldenを更新していない。

## フォルダー一覧の続きを表示する

この機能は[PR78](https://github.com/AIrisu-072/knowledge-platform/pull/78)をmain `09f79a2635b09510e2d0bdeb530ba77881a70e37`へ統合した。[統合後CI](https://github.com/AIrisu-072/knowledge-platform/actions/runs/37384154333)でも201件の表示とHTTPサーバー再起動後の保持を確認した。旧固定版3d8deb2とRoot作成のみのce8ed4fには含まれず、現在pinには含まれる。[続き表示の記録](../superpowers/execution/document-folder-pagination-status.md)を参照する。

1. フォルダー欄で対象の子フォルダーを開く。最初は1回あたり200件を表示する
2. 「さらに表示」があれば押す。その親の続きだけを取得し、既に表示した行とフォルダー選択を保つ。文書一覧下部の「次のページ」とは別の操作である
3. 途中で失敗したら、表示済みの行を確認したまま「続きを再試行」を使う。失敗を一覧の末尾とは扱わない
4. cursorが無効になった場合などは「最初から読み直す」で先頭から取得する。後続ページの表示は読み直すが、選択したフォルダーや未確認の作成要求を新しい操作へ置き換えない

続きはサーバーが返した情報だけを使い、現在読めるフォルダーを取得する。途中の改名・追加や現在権限の変更があり得るため、一覧全体の固定snapshotや総件数を保証する操作ではない。改名・移動・ACL・既読の画面は今回増やさない。

## 選択したフォルダー内に子フォルダーを作る

この機能は[PR79](https://github.com/AIrisu-072/knowledge-platform/pull/79)をmain `5d9e3c46c5b8ed1b5dd8cbe32edefb46482f787a`へ統合した。[統合後CI](https://github.com/AIrisu-072/knowledge-platform/actions/runs/37392942272)でも、通常GUIで選んだ親の子作成とHTTPサーバー再起動後の保持を確認した。旧固定版3d8deb2、Root作成のみのce8ed4f、ページ送りまでの09f79a26には含まれず、現在pinには含まれる。[選択親作成の記録](../superpowers/execution/document-selected-folder-create-status.md)を参照する。

1. フォルダーツリーで、作成先にするSystem Root以外のフォルダー名を押す。必要なら「さらに表示」で対象まで進む。URLのフォルダーIDだけでは作成先の現在行を確認できないため、直接開いた場合もツリーで選び直す
2. 「選択したフォルダーに子フォルダーを作成」を開き、「登録先」の名前とIDを確認する。「System Rootにフォルダーを作成」は別の入口で、保存済みの作成要求や確認結果がない場合のRoot直下への新規作成用である
3. 子の「フォルダー名」と「作成理由」を入力し、「作成する」を押す。元の親の既に表示した範囲を先頭から読み直し、作成先の現在行と現在の操作可否を確認してから送信する
4. 読取りに失敗したり、対象が移動していたり、並びが変わって確認した範囲に見つからなくなった場合は作成を止める。フォルダーツリーを読み直し、同じ作成先の名前・IDを確認して選び直す。存在しないと断定して別の作成先を推測しない
5. 「フォルダーを作成しました。」を確認し、「確認して閉じる」を押す。作成先の子一覧を展開して結果を確認する。一覧の読取失敗だけを理由に再作成しない

Rootと選択親は、進行中または未確認の作成を1つだけ共有して保持する。別の親や別画面へ移動しても、結果確認では保存済みの作成先名・IDを確認する。「同じ内容で再試行」は元の操作ID・新folder ID・作成先・revision・名前・理由をそのまま送り、新しい選択先へ切り替えない。Rootの操作か選択親の操作かを、現在のツリー選択だけで判断しない。

新規送信前の読取り中にキャンセル・別親選択・画面移動をした場合、遅れて戻った読取結果から作成を開始しない。送信後のpending/unknownは消えない。最初の確定拒否の見直しも元の作成先を読み直し、確認できなければ再選択へ止める。ブラウザー再読込・タブ終了をまたぐ保持は保証しないため、未確認のまま離脱せず、解決しない場合は表示された操作IDと作成先IDで管理者へ確認する。

この作成機能に改名・移動・ACL変更・既読操作は含まれない。改名は次節の後続機能である。unknown回復の純粋DOM資格を実通信断試験の合格へ読み替えない。

## 選択したフォルダー名を変更する

この機能は[PR80](https://github.com/AIrisu-072/knowledge-platform/pull/80)をmain `1fe1b011e31477cd7a4de1b7facdcef56a97612d`へ統合した。[統合後CI](https://github.com/AIrisu-072/knowledge-platform/actions/runs/37401300371)でも、子フォルダーの実改名・同要求replay・現在権限・HTTP再起動後の同ID/新名保持を確認した。旧固定版3d8deb2や選択親作成までの版には含まれず、現在pinには含まれる。[改名の記録](../superpowers/execution/document-folder-rename-status.md)を参照する。

1. フォルダーツリーで改名するフォルダー名を押し、「選択したフォルダー名を変更」を開く。現在名とIDを確認する。URLのIDだけでは変更できないので、直接開いた場合もツリーで対象を選び直す。System Rootや権限不足では、サーバーが示す変更不可の理由を確認する
2. 「変更先のフォルダー名」と「変更理由」を入力する。名前の前後空白とUnicode正規化、文字数・禁止文字の規約は作成時と同じである
3. 「変更を保存する」を押す。送信前に現在状態を読み直し、編集中の基準名や更新番号と違っていた場合は入力を保持して停止する。「最新の状態を取得して見直す」で現在名を確認し、希望名と理由を見直してから改めて保存する。自動で外部の改名を上書きしない
4. 変更結果を確認して「確認して閉じる」を押す。現在と正規化後の名前が同じ場合もサーバーへ照会し、変更がない結果を区別して表示する
5. 名前順の位置が変わるため、一覧を再読取して同じIDを確認する。URLのフォルダーIDは保持するが、古い名前のコピーを表示し続けないため、一時的にID表示と再選択案内になる。必要なら「さらに表示」を使う。別フォルダーを選んでいた場合、その選択を勝手に変えない

結果不明では「同じ内容で再試行」を使い、操作ID・対象ID・希望名・理由・期待更新番号を変えない。画面往復後も保存済み要求を確認できる。後続の権限エラーや404を、最初の変更が未実行だった証拠にしない。保存済みの名前は送信時の情報であり、過去の成功を再表示しただけで現在名とは判断しない。現在名は一覧の読取りで確認する。

最初の送信が確定拒否された場合だけ、同じ対象IDをツリーで選び直して「最新の状態を取得して見直す」を使う。移動後や名前順の別ページでも、同じ対象を実際に選び直した根拠だけを使う。別対象やURLだけへ要求を差し替えない。「拒否された操作を確認して終了」は確定拒否の終了であり、pending/unknownを破棄する操作ではない。

作成または改名が送信中・結果不明の間は、もう一方の新規操作を先に始めない。保存済み要求の同一再送と結果確認は継続できる。解決前のページ再読込・タブ終了を避け、解決できなければ操作ID・対象IDを添えて管理者へ確認する。名前の再読取失敗だけを理由に改名を再作成せず、成功した操作と表示の更新失敗を区別する。

実hosted資格は子1件の実変更・固定replay・現在権限・HTTP再起動後の保持に限る。実no-opと実文書のfolderName更新は今回の追加runtimeに含めず、純粋/DOMの確認と区別する。通信断fault、移動・ACL変更・既読、画像比較の資格も追加しない。

## 選択したフォルダーを移動する

この機能はPR87で既存Folder移動APIを通常GUIへ接続し、現在pinに含まれる。旧固定導入版 `0801c986` には含まれない。公開製品headの実資格は[手動導入手順](linux-manual-installation.md)を正本とし、[移動の状況と計画](../superpowers/execution/document-folder-move-status.md)の実装時点の記録と区別する。ローカルGUI952件/42 suites・独立SOURCEレビューGOはローカル資格であり、下記の実hosted資格や実サーバーへの反映とは分ける。

1. 通常のフォルダーツリーで対象を選び、「選択したフォルダーを移動」を押す。対象ID・現在名・現在の親IDを確認する。直接URLを開いただけの場合はツリーで選び直す。System Root自身は移動できない
2. 「移動先フォルダー」の「移動先を選択」で別の親を明示選択し、移動先ID・名前を確認する。System Rootも移動先に選べる。候補を読めることや候補自身の操作可否だけで、移動が必ず許可されるとは判断しない
3. 「移動理由」を入力する。継承アクセス設定の変化で、配下や自分の閲覧・編集権限が変わる可能性があることを確認し、「継承アクセス設定への影響を確認しました」にチェックする。完全なACL差分や影響人数を表示する機能ではない
4. 「移動する」を押す。対象と移動先を送信前に読み直し、名前・更新番号が変わっていれば理由を保持して停止する。「最新の状態を取得して見直す」で確認し、影響へのチェックもやり直す。対象が見つからない場合や別親へ移っていた場合は、通常ツリーで同じ対象を選び直す。最終の認可・循環・公開予約・更新競合はサーバーが検査する
5. 「フォルダーを移動しました。」を確認して「確認して閉じる」を押す。同じ親への要求もサーバーが検査し、親が変わらなかった結果を区別して表示する。結果画面の名前・親・移動先は送信時の記録であり、現在状態は更新されたツリーで確認する
6. 移動先を開き、同じID・名前の対象を選び直す。旧親から対象が消え、現在親が移動先になったことを確認する。一覧の続きが初期化された場合は、先頭から「さらに表示」を使う。URLの対象IDや別画面の現在選択を勝手に戻さない

結果不明では「同じ内容で再試行」を使い、操作ID・対象ID・移動元・移動先・期待更新番号・理由を変えない。後から403・404・競合が返っても、最初の移動が未実行だった証拠にはならない。保存済みの要求を保持し、管理者へ操作IDと対象IDで確認する。最初の確定拒否だけは「最新の状態を取得して見直す」、または「拒否された操作を確認して終了」で扱う。同名衝突の競合では、対象と移動先の現在状態を確認してから見直す。

作成・改名・移動のいずれかが送信中または結果不明なら、他の新規操作を始めない。同じアプリ内の画面往復で未確認の要求を保持するが、ページ再読込・タブ終了をまたぐ保持は保証しない。成功結果が確定した後の表示更新失敗は移動失敗と区別し、移動を新しく作らず読取を再試行する。

今回追加する実受入は、既存201兄弟の別親へ改名済みの子を1回移動し、旧親・移動先の現在GET、新しいcursorによる200件＋1件、通常ナビ往復、HTTP 2 process再起動後の現在親・同ID・同名・revision 2と元create/rename/move receiptの固定replayを確認する範囲である。実hosted実行の結果は上記記録を正本とし、ローカルの純粋試験・型検査を実受入合格へ読み替えない。同名衝突・rollback・台帳/監査不変は同機能の既存DB/HTTP反例で扱う。公開されないaccess_revisionの数値、実の権限変化、GUI通信断、PostgreSQL process再起動、画像比較、対象PC・本番Identityの資格は追加しない。

## 公開一覧で未読の文書だけを表示する

この機能はPR81統合main `0801c986` を基点にPR82で統合した。旧固定導入版0801には含まれず、現在pinには含まれる。[未読条件の状況](../superpowers/execution/document-unread-filter-status.md)の初回受入履歴と、[手動導入手順](linux-manual-installation.md)の公開製品headの資格を区別する。

1. 「文書」の公開一覧を開き、「未読のみ」を選んで「絞り込む」を押す。チェックを変えただけでは適用しない。文書名・3属性・フォルダーの条件と併用できる
2. 現在の利用者が現行公開版について既読を記録していない文書を、サーバーが現在読める範囲から表示する。以前の版を既読にしていても、現在の公開版についての判定を使う
3. 未読条件だけ外すときはチェックを外し、もう一度「絞り込む」を押す。他の条件は保持し、最初のページから表示する。「属性の絞り込みを解除」は3属性だけを外し、適用済みの未読条件は変えない
4. 次のページ・詳細との往復・ブラウザーの戻る/進むでも適用済みの未読条件を保持する。条件解除時は既存の読取cacheを使う場合があり、必ず新しい通信をするとは限らない

「未読のみ」は公開一覧専用で、「編集作業」や履歴一覧には追加しない。URLへ不正な値や対象外の一覧との組合せを直接指定した場合は理由を表示して取得を止める。「条件を解除して一覧へ戻る」で、不正な条件を明示的に解除する。属性と未読条件が同時に不正なら両方を解除し、他の有効な条件を保持する。

絞り込み・閲覧・ファイル取得だけで既読にはしない。既読を記録するGUIは今回追加していない。今回の実受入対象は既存未読文書の取得・往復・HTTPサーバー再起動・本人/Agent readState不変で、実の既読行が除外されることや本人と他人の既読差は新しいruntime資格として主張しない。純粋/DOM、既存DB契約、今回の実操作確認を区別する。未確認の変更要求は同じアプリ内で保持するが、ページ再読み込み・タブ終了をまたぐ保持は保証しない。

## 文書を初めて登録する

1. 「文書」または「編集作業」の一覧で登録先フォルダーを選び、「文書を登録」を押す。全体表示ではルートへ登録する。Organizationの初回手順では「文書」から「System Root」を明示選択する。「PoC Shared」は別のDocument PoC fixtureである
2. 登録先を確認し、文書名とブラウザーを開くPC側の原本ファイル1件を指定する。1ファイル256 MiB以下にする。初回登録は単原本で、複数原本の同時登録は含まない
3. 「下書きとして登録」を押す。登録が確認できるとauthoring用途の「版・改訂」へ自動で移動する
4. 登録直後はWORKINGの下書きで、正式改訂や公開版はまだ無い。公開する場合は対象と原本を確認して「公開する」を開く。「今すぐ公開」を選び、「公開対象の版とファイルを確認しました。」にチェックする
5. 画面の「公開する」を押し、「公開を確認」ダイアログで対象を再確認して「確定する」を押す。公開成功後、必要なら「概要」の「記録・技術情報を確認」から `Document ID` を控える。公開確定が結果不明なら、次の「公開・予約公開の結果が不明な場合」に従う

初回登録の通信結果が不明なときは、同じ文書を再登録しない。画面に「登録結果を確認」があればその照会を使い、なければ編集作業の一覧や管理者に結果を確認する。初回登録には重複を防ぐ操作IDが無いため、取下げ・公開終了と同じ再送はできない。

## 公開・予約公開の結果が不明な場合

公開・予約公開の確定結果が不明なら、未公開や旧公開維持と断定せず、確認ダイアログの「同じ内容で再試行」で同じ操作ID・同じ対象・同じ要求を再送して結果を確認する。要求は公開画面の一時状態に保持されるため、版の変更、公開方法・予約日時の変更、公開画面の開き直し、画面からの離脱、ページの再読み込み、タブ終了を避ける。既に元の要求を失った場合は新しい公開要求を送らず、管理者に元の操作結果を確認する。

## 文書共通の属性を編集する

1. 対象文書の「概要」で「メタデータを編集」を押す。現在の権限・状態で操作できない場合は、画面の理由を確認する
2. 「文書種別」「所管部署」「カテゴリ」の必要な項目を編集する。対象は文書共通の `document_type`、`owning_department`、`category` で、版の属性とは別である
3. 値を削除するときは、その項目の「削除」にチェックする。空文字や空白は値として保存されるので、削除の代わりに空欄にしない。旧形式の属性やその他の属性・extensionsは保持する
4. 「変更理由」を入力して「保存する」を押し、更新結果を確認する。キャンセルでは変更しない。未公開の文書では正式改訂を作らず、公開済み文書の実変更では既存のMinor改訂を記録する。無変更は新しい正式改訂を作らない
5. 保存結果が不明なら「同じ内容で再送」を使い、同じ操作ID・対象・期待revision・内容で確認する。画面上の値が一致しただけでは成功と判断しない。確定拒否後は「最新の内容を読み直す」で現在の情報を確認する

未確認の要求は起動中のアプリのメモリーだけに保持される。解決前にページを再読み込みしたりタブを終了したりしない。予約中は先に現在の予約を確認し、取り消す必要がある場合は次の予約取消手順を使う。

## 正式改訂の続きを表示する

以下は正式改訂の続き表示を含むsourceでの手順であり、上記の固定導入版 `cd6aafcc` には未収録。

1. 文書詳細の「版・改訂」を開き、「正式改訂」を確認する。正式な改訂番号の履歴と、上にあるWORKINGなどのコンテンツ版は別の一覧である
2. 最初は新しい順に100件まで表示する。「さらに表示」があれば押して続きを加える。最後まで取得すると続きのボタンはなくなる。読み込み中の連打で同じページを重複追加しない
3. 続きの一時的な読取失敗では、それまでの改訂を保持する。「続きを再試行」で同じ続きから再開する。権限を確認できない場合や続きの位置が使えなくなった場合は、エラーを確認して「最初から読み直す」を使う。読取失敗を「正式改訂なし」とは表示しない
4. 「基準」「対象」を選んで「新旧比較」を開く。選んだ改訂はtabの往復や先頭からの読取でも保持する。選択した古い改訂がまだ取得されていない場合は、比較を止めて未取得の選択と表示する。続きを取得するか、取得済みの改訂から明示的に選び直す。別の改訂へ自動で置き換えて比較しない。比較画面からは「← 版・改訂へ戻る」で戻る
5. 「最初から読み直す」で表示と現在の読取可否を確認し直せる。これによって公開・版更新・文書移動などの未確定操作を取り消したり、新しい操作として送り直したりはしない

実操作受入の対象は既存の正式改訂2件の通常表示・明示比較・再読取・HTTP再起動後の表示である。100件＋1件の追加表示、途中失敗・失効等はDOM試験の範囲である。既存APIのページ分割試験とは区別し、実GUIの100件超を試験済みとは扱わない。見た目全体の画像比較も未取得のままである。

## 文書を別のフォルダーへ移動する

以下は文書移動GUIを含むsourceでの手順であり、上記の固定導入版 `cd6aafcc` には未収録。フォルダーそのものの移動とは別の操作である。

1. 通常の公開一覧または「編集作業」から文書の詳細を開き、「文書を移動」を押す。現在の文書情報と元の所属を読み直す。元所属を表示できない文書、終了後の文書、読めない移動先はこの画面の対象外で、URLのIDから補って操作しない
2. 移動先ツリーで読めるフォルダーを選び、文書名・文書ID、元所属名・ID、移動先名・IDを確認する。System Rootも移動先に選べる。移動先が見えていても移動できる保証にはならず、最終的な認可はサーバーが確認する
3. 移動理由を入力し、継承アクセス設定への影響を確認する。文書の明示アクセス設定は保持する。継承中は移動先の設定が適用され、自分を含む閲覧・編集権限が変わる可能性がある。画面は権限の差分や影響人数を予測しない
4. 「移動する」を押す。送信直前にも文書と移動先を読み直す。状態が変わっていたら理由を保持して停止するため、「最新の状態を取得して見直す」から内容を再確認する。予約公開中の移動は先に現在の予約を確認し、必要に応じて取消手順を使う
5. 「文書を移動しました」または「所属の変更はありませんでした」を確認する。正式改訂・Version・原本・既読状態は変えない。移動結果の表示は操作時点の記録で、現在の所属は新しい読取結果で確認する。表示更新に失敗しても、確定した移動結果が未確定に戻ることはない

結果が不明な場合は「同じ内容で再試行」を使う。同じ文書ID・操作ID・元所属・移動先・期待revision・理由を保持し、新しい要求でやり直さない。後の再送が403や409になっても、最初の移動が未実行だったとは判断できない。管理者へ操作IDを伝えて確認する。

閉じたり別の画面へ移動した場合は、通常の文書一覧または文書詳細にある「文書移動の保持結果を確認」から同じ要求を開ける。移動後に文書を閲覧できなくなっても、文書一覧の入口を使える。結果不明の間は新しい文書移動・フォルダー作成・改名・移動を始めない。要求は開いているアプリのメモリーだけに保持されるため、ページ再読み込みやタブ終了を避ける。

## 作業版の原本を差し替える

1. メインナビゲーションの「編集作業」で文書の「版・改訂」を開く。Organizationのタスク画面や公開文書の詳細からも移動できる。WORKINGがあるときは「作業版を編集」、現公開版だけのときは「新しい版を作成」を押す
2. 一覧の原本を確認し、変える原本の「差替ファイル」を選ぶ。複数原本を扱えるが、原本の追加・削除・並替・形式変更は今回含まない。論理位置と順番は保持する
3. 選択した原本に変換ファイルがある場合、新作業版へ引き継がない対象・件数を確認する。変えていない原本と変換物、旧公開版のファイルは保持する。自動再生成はしない。作業版だけにあった変換物は除外後の永久取得を保証しない
4. 「作業版を保存」または「新しい作業版を作成」を押す。保持する全ファイルを監査付きで取得してから、全manifestを送信する。途中の取得失敗や権限失効では保存しない
5. 作業版を保存するだけでは公開中の版を変えない。内容を確認して既存「公開する」で確定すると、新版へ一度に切り替わる。取下げを先に行う必要はない。公開確定の応答が不明なときは、旧公開版が維持されているとは断定せず、上記の「公開・予約公開の結果が不明な場合」に従う

初回未公開WORKINGも同じ版ID・番号のまま編集できる。未検査・検査不能だった初回原本の修復では旧原本の再検査を前提としないが、新原本の検査と既存mediaTypeの保持を必要とする。予約中は先に予約を取り消す。古い公開版を基準にした作業版は通常更新できない。現公開があるときは「現行版へ基準を更新」を押し、対象の現公開版を確認して「基準更新を確定」を使う。原本・補助ファイル・版番号を変えず、公開も行わない。公開版・取下げ済み版・公開終了した文書を直接変更しない。

編集中に背景の再取得で対象版・revision・用途が変わったり読取りに失敗したりすると、未送信の文書名・選択ファイルを保持して保存を止める。明示的な「最新状態を確認」が成功し、新しい編集基準が採用されたときは、未送信の文書名・選択ファイルが初期化される。実行前に必要な文書名を控え、採用後に文書名を入力し直して差替ファイルを選び直す。読取りの失敗や保存結果不明（UNKNOWN）を強制リセットする操作ではなく、UNKNOWNでは同じ内容の再試行で先に結果を確認する。自動保存・自動mergeは行わない。

再送に必要な原本・変換物は全て合算する。最大binary63件、各256MiB、JSON1MiB、headers等を含む全体1GiBと既存120秒の処理制限がある。共有FileIdや上限で全保持を保証できない場合は理由を表示して停止し、一部だけ保存しない。

結果不明は「同じ内容で再試行」で操作ID・対象・revision・全bytesを変えず回復する。別文書へ移動しても同じ起動中は未確認の要求を保持する。ブラウザーの再読込やタブ終了は避ける。確定拒否は「最新状態を確認」後、改めて保存する。公開切替後に古いpublished URLを使った新規取得が404になる場合は再読込する。historyへ勝手に切り替えない。

## 公開予約を取り消す

1. 「編集作業」から予約済みの文書を開き、「版・改訂」で対象WORKING版を選ぶ
2. 「公開予約を取り消す」を押し、文書・対象版・予定日時を確認する。予定日時にはAsia/TokyoとUTC offsetを表示する
3. やめる場合は「戻る」を押す。この時点では予約は取り消されない
4. 「予約を取り消す」を押し、「公開予約を取り消しました」を確認する。作業版と原本は保持される。改めて予約する場合は「予約公開する」から別の予約を行う

ボタンは現在の予約IDと現在capabilityが読み取れた場合だけ表示する。確認中に予約実行・再予約・権限変更があった場合は最新状態を確認する。取消結果が不明なら「同じ内容で再試行」を使う。以前の予約IDを維持して照合し、新しい予約を代わりに取り消さない。閉じた後は「未確認の取消を開く」から再開する。ページ再読込・タブ終了をまたぐ自動回復は保証しない。

Organizationの手動導入ではschedulerを起動しない。この取消GUIや予約日時の表示だけで自動公開が稼働するとは扱わない。[Document PoCのscheduler起動例](document-poc-runtime-v0.md#scheduler-and-other-boundaries)は `KP_RUNTIME_MODE=poc` 用で、`organization-synthetic` のrequesterを解決しないため流用しない。

## 現行の公開版を取下げる

1. 通常の「文書」一覧から公開中の文書を開き、「版・改訂」を選ぶ
2. 現行公開版を確認し、表示される「選択版を取下げ」を押す。表示がない場合は現在の権限・状態を確認する
3. 理由を入力し、対象と影響を確認する。取りやめるときは「キャンセル」を押す。この時点では送信されない
4. 「取下げを確定」を押し、結果を確認する

現行版の取下げ後は、サーバーが直前の公開版の安全性を確認できればその版へ復帰する。復帰できる版がなければ、現行の公開版は無くなる。画面はサーバーが返した結果を表示する。遠い過去版への自動復帰はしない。文書全体の公開を必ず終えたい場合は、次の「公開を終了」を使う。

今回の画面追加は通常公開画面からの現行版に限定する。「編集作業」はWORKINGの操作用で、過去の公開版を選んで取下げる画面は別途追加予定である。

## 文書全体の公開を終了する

1. 公開中の文書の「版・改訂」で「公開を終了」を押す
2. 文書全体が対象であることを確認し、理由を入力する
3. 次の影響を確認して「公開終了を確定」を押す
   - 通常の公開閲覧を終了し、その文書の公開予約を無効にする
   - 元の公開版・過去版・原本は保持する
   - 現行v0では通常の版作成・公開操作から再公開できない
4. 「文書の公開を終了しました」を確認する。公開終了後に詳細読取が「文書が見つからないか、閲覧できません」となるのは、通常の読取から外れた結果である

取下げと公開終了は異なる操作である。取下げ後には直前版へ復帰する場合があるが、公開終了は現行版を無くして通常公開を終了する。

## 結果不明・競合・権限失効

- 取下げ・公開終了で結果不明と表示されたら、「同じ内容で再試行」を使う。操作ID、対象、理由、期待するrevisionを変えずにサーバーへ照会・再送する
- 閉じたり、同じアプリ内で別文書へ移動しても未確認の操作は保持する。対象文書へ戻り「未確認の操作を開く」から続ける
- 未確認の操作がある間はブラウザーの再読み込みやタブ終了を避ける。操作要求はこのアプリ起動中のメモリだけに保持する。警告を無視して閉じた場合の自動回復は保証しない
- 競合や権限失効などの確定した拒否では「最新状態を確認」を押し、現在の対象・権限を確認してから新たに操作する。自動で新しい操作IDを作って再送しない
- すでに結果不明だった操作が、その後403などで拒否されても、最初の操作が未実行だったとは判断できない。同じ未確認操作を保持し、権限と操作履歴を管理者に確認する
- 照会IDが表示されたら問い合わせ時に伝える。文書内容や秘密情報を公開の問い合わせ先へ送らない

## 今回追加しない操作

過去版選択の取下げ、原本の追加・削除・並替、初回文書登録自体の複数原本化は別途扱う。予約取消の読取補修は既存予約IDの追加に限り、予約/取消の業務意味や新しい権限規則は変更しない。
